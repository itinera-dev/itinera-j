# itinera-j: tier 1 plan

A general plan for implementing tier 1 of the Itinera specification on the JVM: a core written in Kotlin, a Kotlin layer with both execution modes, and a Java layer for synchronous workflows, built together and each proven by the conformance cases. It is modelled on the TypeScript plan, itinera-ts `docs/tier-1-plan.md`, and on how itinera-rs built tier 1, and keeps their answers wherever the question is not about the language. It is a draft: every decision, 1 to 15, was taken with the maintainer, on 2026-10-21, 2026-10-23 and 2026-10-27. It was written before the repository existed and moved here in stage 0, which settled what the plan left to it: the tooling's versions, the checks it re-made on the pinned Kotlin, and four corrections where the cases or the other languages had moved on.

Behaviour comes only from the [specification](https://github.com/itinera-dev/spec/tree/main/spec). Where this plan and the specification disagree, the specification is right. Code samples show the intended shape only; the tech specs record the final names.

Claims marked "Verified" were checked on 2026-10-21 and 2026-10-23 with a small Gradle project on JDK 21, Kotlin 2.2.20, kotlinx-coroutines 1.10.2 and kotlin-reflect 2.2.20, compiling Kotlin and Java sources together, and the deep-copy libraries compared in section 2 at their newest versions. Stage 0 made the checks that concern the language again on 2026-10-27, on the pinned Kotlin 2.4.21 and kotlin-reflect 2.4.21, with Kotlin compiled for JVM 17 and `apiVersion` 2.3: a Java `switch` with record patterns over `@JvmRecord` members of a sealed interface, with no `default`, compiles and runs on JDK 21; javac 17 at release 17 refuses a Java class implementing a sealed Kotlin interface and compiles its twin; a Java class calls an interface's default method; a `suspend` function started with `startCoroutine` and an empty context completes before the call returns; `KFunction.isSuspend` tells a `suspend` function; kotlin-reflect and `typeOf` tell `List<Long?>` from `List<Long>`; Java writes `@Input("amount")` for an annotation whose argument is named `value`, and javac refuses the shorthand for another name; and repeatable annotations keep their written order, read from Kotlin and from Java. All held.

## What this plan implements

- **Specification 0.1.0, tier 1**, checked by the conformance cases at **`v0.1.0-rc.18`**, the newest tag on 2026-10-27, and by every later candidate as it is tagged.
- **The proposals**, the 35 of tier 1 and test support that itinera-rs lists and itinera-ts plans: 0002, 0003, 0008, 0009, 0010, 0011, 0012, 0024, 0027, 0032, 0040, 0041, 0042, 0049, 0054, 0055, 0056, 0057, 0058, 0060, 0061, 0062, 0063, 0064, 0065, 0081, 0083, 0085, 0091, 0095, 0098, 0102, 0104 and 0106, which make up tier 1, and 0108, test support, listed because this plan claims `testing`, and the four accepted since: 0116 (duplicate adapter names), 0119 (attempt mistakes in test support), 0121 (copies that keep received data read-only) and 0122 (custom code that returns an unexpected result). Proposal 0113, value conversions, is not listed, since proposal 0121 says the copies this plan makes are not value conversions (section 3). Proposal 0111 has no cases: its suggested names are the names this plan uses, in camelCase, as the specification itself spells them for Kotlin.
- **Two claims, one per language** (decision 14), each with its own manifest and report: Kotlin claims `sync` and `async`, one mode per workflow (decision 2), and `testing`, with test support in its own artifact (decision 10); Java claims `sync` and `testing`. Both list the same proposals. Their rules made impossible are the same but for two that Java can write and Kotlin cannot: `unexpected-result` and `non-string-journey-id`, since Java can return `null` (proposal 0122), which only the Kotlin manifest lists (see "Rules made impossible, and rules enforced at run time"). Not `value-conversions`: values are copies of the application's own objects, read by their runtime type, and proposal 0121 says such copies are not value conversions (decision 5, section 3).
- **Rules made impossible to express:** `bag-write` by the types, and, by the types and a signature check before any instance (decision 11), `invalid-lifecycle`, `rescue-skip`, `journey-scope-request` and `mode-not-accepted`, which the types refuse with the builder and the descriptor interfaces but which annotated code can still write, refused when the workflow is described, before any instance. `attempt-fraction` too, since an attempt number is an `Int`. In the Kotlin manifest only, `unexpected-result` and `non-string-journey-id`, which Kotlin's types rule out, with a signature check for annotated code, and Java's do not. The others, `no-instance` among them, are enforced while the workflow is described or while the journey runs, and their scenarios run (see "Rules made impossible, and rules enforced at run time").
- **When the cases move.** When the specification and conformance are tagged `v0.1.0`, a pull request moves `cases` to it; any case changed after the pinned candidate gets a `spec update` issue, as PROCESS.md says.

## Who it is for, and how the languages share it

Decided by the maintainer on 2026-10-23 (decisions 1, 12 and 13), after the plan of 2026-10-21 had made Java an equal of Kotlin in every part:

1. **The audience**, in order: synchronous Kotlin on backends; asynchronous Kotlin on backends; synchronous Java on backends; and one day Kotlin, in both modes, on Android. Java still dominates enterprise backends, so Java matters most to the project, though Kotlin is the primary implementation: the Java layer grows with every stage from stage 3, and the first release ships both languages (decision 14).
2. **Kotlin is the primary implementation.** The core is written in Kotlin, and the book comes in Kotlin first. Java gets a thin layer over the same core, never a second engine: the engine is `suspend` code, which only Kotlin writes naturally, and one value walk and one engine serve both languages.
3. **Java is synchronous only.** Java writes synchronous workflows and runs them on `LocalExecutor`, on virtual threads if it wants cheap blocking. Java has no `suspend` and no await; asynchronous Java would mean `CompletionStage` forms everywhere, which is the complexity the maintainer chose to drop.
4. **Java users carry only Kotlin's standard library.** kotlin-reflect and kotlinx.coroutines are needed only for Kotlin classes and the asynchronous executor, so they live in `itinera-kotlin` (section 1). The standard library, about 1.7 MB, cannot be left out, since every compiled Kotlin class calls it; many Java backends already carry it through OkHttp or Retrofit.
5. **One repository, one version.** The repository holds every artifact as a module of one Gradle build, released together (section 1).

### What keeps the core reachable from Java

The core's public API is what both layers expose, so it avoids what Java cannot use. Five rules, none of which changes how Kotlin code reads:

1. **Names are small final classes**, `StepName.of("charge")`, not value classes, whose names are mangled in bytecode and hidden from Java.
2. **The synchronous builder takes `fun interface`s**, not Kotlin function types, so its signatures name what each function is, such as a step's run or a provider, a Java lambda fits each as itself, and one that returns nothing is `void`, never `Unit.INSTANCE`.
3. **Factories are static from Java**: companion-object factories carry `@JvmStatic`, and functions with default arguments `@JvmOverloads` where Java needs the shorter forms.
4. **Events and the result are `@JvmRecord` data classes** under sealed interfaces, so Java 21 matches them with `switch` and record patterns, and Kotlin with `when`. Verified: a Java `switch` with a record pattern over a Kotlin `@JvmRecord` member of a sealed interface compiles and runs. Kotlin writes the `PermittedSubclasses` attribute at JVM target 17, so javac refuses a Java class implementing one of itinera's sealed interfaces, such as `Outcome`, `RescueOutcome`, `OnSuccess` or `OnFailure`, which two exclusions rest on ("Rules made impossible, and rules enforced at run time"); verified, with javac at release 17 refusing a Java class implementing a Kotlin `sealed interface OnFailure` that `KeepDefault` shares with `OnSuccess`, and its twin compiling. The JVM checks the same attribute when it loads a class, so no class compiled otherwise gets past it. A Java `switch` over events with no `default` is exhaustive (verified in stage 0).
5. **Every reified call has a form taking a type token.** The core does the work in an ordinary function taking a `TypeToken<T>`, which holds the full type, generics included, and whether `null` is of it, at the top and for each type argument, as `TypeToken.of(Long::class.javaObjectType)`, `TypeToken.ofNullable(...)` or, for a generic type from Java, `new TypeToken<List<Long>>() {}`. Whether `null` is of the type itself is said by the factory that makes the token, so a builder's author states it, as a Java parameter's annotations say it (section 2); in the anonymous form, `new TypeToken<@Nullable Long>() {}` admits `null` and `new TypeToken<Long>() {}` written in `@NullMarked` code excludes it. The type arguments of a token made from a Java type admit `null`, as an unmarked Java parameter's do, unless JSpecify marks them: `new TypeToken<List<Long>>() {}` written in `@NullMarked` code refuses a `null` element, and `new TypeToken<List<@Nullable Long>>() {}` admits one, read through `getAnnotatedSuperclass`, which stage 1 verifies on JDK 17 and 21, since javac has had bugs writing type annotations on an anonymous class's supertype. Kotlin code that wants `List<Long>` to refuse a `null` element uses the reified form. A token never holds a primitive: `TypeToken.of(long.class)` gives the token of `Long`. `itinera-kotlin` adds the reified sugar, `data.read<Long>("amount")`, which builds the token from `typeOf<T>()`, from the standard library, so it keeps Kotlin's nullability, `List<Long?>` included, which a `java.lang.reflect.Type` cannot hold. The engine needs the type as a value anyway, to check a stored value against it.

Interface method bodies compile as JVM default methods, so a Java class implementing `ItineraStep` calls `succeed()` as any default method (verified). Annotations read the same from both languages: one usually written with one argument names it `value`, so Java writes `@Input("amount")` (verified, including that another name breaks the Java shorthand), and `@WithStep` names its first argument `step`. An annotation that takes several arguments, as its Rust macro does, names them as Rust does, such as `@Workflow(name = "orders")`. A Java test source set compiles against `itinera` alone from stage 3, so the five rules are checked from the start, beside the Java conformance runner (sections 15 and 16).

### How each language meets only its own part

1. **Asynchronous code is out of Java's reach.** Every asynchronous type, `ItineraAsyncWorkflow`, `AsyncReporter`, the asynchronous builder and `AsyncLocalExecutor`, lives in `itinera-kotlin`, which a Java application does not add. Every `suspend` function carries `@JvmSynthetic`, which javac cannot see or call, so adding the artifact does not change that, and a Java class cannot write a `suspend` function to implement an asynchronous part. A Java class in an asynchronous workflow has no `suspend` `run`, so it is refused as a part of the other mode when the workflow is described. javac still accepts a Java class that implements an asynchronous interface and writes none of its `suspend` operations, which it cannot see, so such a class is refused as a part of the other mode too: a reporter or a hook by `run`, with `mode not accepted`, and a dispatcher factory by `AsyncLocalExecutor`'s constructor. A class counts as written in Java when it has no `@Metadata` and is not the hidden class of a lambda, so a mock that Mockito or MockK generates and a `java.lang.reflect.Proxy`, which carry no `@Metadata` either, are refused the same way: tests stand in for an asynchronous part with a Kotlin class or lambda.
2. **Kotlin classes need `itinera-kotlin`.** Plain Java reflection cannot see Kotlin's nullability, `suspend`, a data class's primary constructor or a `data object`. The core recognises a Kotlin class by the `@Metadata` annotation the compiler puts on every one, itinera's own classes excepted, and refuses it when the workflow is described if `itinera-kotlin` is missing, saying to add it. A data class captured as a value without it is not a value, unless it is a `@JvmRecord` data class, which is a record and which the core walks as one; a `data object` is not a value without it. The documentation's first page says Kotlin applications add `itinera-kotlin`, and the bill of materials makes it one line.
3. **The Java face stays out of Kotlin's way.** `Optional` requests and Java's other forms live in `itinera-java`, which Kotlin applications do not add; Kotlin can call any Java API, so nothing forbids it, and nothing breaks if it does.
4. **CI holds the line**: two sets of Java code compile without `itinera-kotlin`: the usage tests of the core against `itinera` alone, and the Java conformance runner, its fixtures and the Java consumer project against `itinera-java`; a Java compile-fail test, compiled with `itinera-kotlin` on its class path, shows `AsyncLocalExecutor.run` cannot be called; the ABI dump of each artifact shows every change to what it exposes.

### Android, later

Android runs the same bytecode on ART, so the design holds, but four things must stay true from the start, so that Android support is an addition and not a rewrite (decision 12):

1. **Reflection lives at the edges.** Only the annotation readers, the value walk and the lending of roles through `java.lang.reflect.Proxy` use reflection, each behind an interface, and `TypeToken` reads its own generic superclass once, when made, as Gson's does on Android; the engine and the rest of the builder never do, but for checks of what a class is marked or made as, `isAnnotationPresent`, `isInterface` and `isHidden`, which read none of its members and need no keep rule beyond the annotation itself, and the engine's reading of a lent instance's class name to name the implementation on events (decision 17). A later step, which decision 4 did not take for tier 1, could generate descriptors with KSP and replace the readers. That removes reflection from describing workflows, but not kotlin-reflect: the walk of data classes and the nullability of their components still read Kotlin's metadata at run time, so removing it from phones would also need generated value walkers, or `kotlin-metadata-jvm` in its place, with `itinera-kotlin` split accordingly. Code generated this way is also what Kotlin Multiplatform would one day need.
2. **The core uses no JDK class Android lacks** at the API level chosen then: records and `RecordComponent` arrive only at API 34, `java.time` at 26, `List.of` and `List.copyOf` at 30. Below API 34, D8 desugars records into ordinary classes, for which `Class.isRecord()` is false: the core's own events and result still work, as ordinary classes, but the value walk does not see an application's records as records there. The value walk handles records only where the class exists; when Android support lands, its stage chooses the floor, or a fallback for desugared records, and verifies `RecordComponent` on ART, and an API check, Android lint or animal-sniffer, joins CI.
3. **Keep rules ship with the artifacts**, so R8 does not strip the annotations, `kotlin.Metadata`, the parameter names reflection reads, or the `META-INF/services` entries that plug in `itinera-kotlin`; written when Android support lands.
4. **Coroutines and `java.lang.reflect.Proxy` already work on ART.** The Kotlin conformance runner gains a run on ART then (section 15). ART does not enforce `PermittedSubclasses`, and D8 may strip it, so on Android the exclusions of `invalid-lifecycle` and `rescue-skip` rest on javac's check alone; the Android stage records that.

## What carries over from Rust and TypeScript, and what does not

| Rust's answer | TypeScript's answer | On the JVM |
|---|---|---|
| Macros are the API applications write, expanding to a public builder | Classes with decorators, filling a public builder's lists | Annotations on plain classes implementing itinera's interfaces are the main API, read by reflection into the same descriptors a public, typed builder makes; the builder is the core, as in Rust (decision 3) |
| Rules impossible by types, each proven by a compile-fail test | Rules impossible by types, proven by type tests | Two impossible everywhere, four more impossible with the builder and the descriptor interfaces and refused before any instance in annotated code (decision 11), and two more in Kotlin only, each proven; the rest run |
| One engine written as asynchronous code, driven synchronously with a waker that does nothing; a workflow is all synchronous or all asynchronous | One asynchronous engine, one executor | One engine written as `suspend` functions, driven synchronously with a continuation that needs no dispatcher, and asynchronously on coroutines; a workflow is all synchronous or all `suspend`, and each of the two executors runs one kind (decision 2). Verified |
| Values are `Serialize + Clone`; every receiver gets its own clone | Plain JSON data, or classes that serialise themselves | The application's own objects, of the shapes itinera accepts, checked by their runtime class, copied into a private copy when captured, and read by their runtime type, as Rust reads exact types. Every receiver gets a fresh copy of its own, as Rust's clone, which proposal 0121 requires of a copy that calls application code. Nothing is serialised (decision 5) |
| Reads name a Rust type | Every request's type is a Standard Schema validator | A request's type is its parameter's declared type, generics included, which reflection reads; the builder names it with a typed token |
| One crate a user adds, `itinera`, over `itinera-core` and `itinera-macros` | One package with subpaths | One artifact per language face, `itinera-kotlin` and `itinera-java`, over the core `itinera`, in one repository and one version; each artifact has packages of its own |
| Step statuses are private; the runner derives them from the events | The same | The same |
| Decision logic is a pure function | The same | The same |
| One emitter, replaceable clock | The same | The same |
| Guards around each reporter | One wrapper around hooks and reporters | One wrapper, as itinera-ts decision 13 |
| `Interrupted`, the executor's own signal | An unexported error class | An exception class private in bytecode, thrown from the emit call; the abort is recorded before it is thrown |
| `&mut self` makes concurrent journeys impossible | A run-time refusal | A run-time refusal |
| Panics are never caught | Every throw is caught | `java.lang.Error` and its subclasses are never caught, as the last point of chapter 5, 5.10, on unrecoverable failures, names them; every other `Throwable` is a recoverable failure |

The four "Notes for other languages" at the end of the Rust plan all apply: a step's reporter is a small per-attempt object holding the dispatcher privately; the executor records the abort before throwing into a step, with the exception class unreachable; input adapters are found by reflection, here on annotated methods of the workflow class; and policies are rebuilt per attempt and per journey to keep hooks stateless.

## Architecture

### 1. Repository, artifacts and packages

- **The repository** is `itinera-dev/itinera-j` (decision 13), one Gradle build with the Kotlin DSL (decision 7), with a module per artifact, as itinera-rs keeps `itinera`, `itinera-core` and `itinera-macros` in one workspace. A change to the core and what it does to each layer land in one pull request.
- **Published artifacts**, one version for all, with a bill of materials:

  | Artifact | Holds | Brings |
  |---|---|---|
  | `itinera` | Values and the data bag, events, synchronous reporters and dispatchers, the base interfaces and annotations, the synchronous builder, descriptors, the instance, the engine, `LocalExecutor`, the token forms, and the annotation reader and value walk for classes written in Java and for JVM records | Kotlin's standard library only |
  | `itinera-kotlin` | `ItineraAsyncWorkflow`, `AsyncReporter` and asynchronous dispatchers, the asynchronous builder, `AsyncLocalExecutor`, the reader and value walk for Kotlin classes (nullability, `suspend`, data classes), and the reified sugar | `kotlin-reflect` and `kotlinx-coroutines-core` |
  | `itinera-java` | The Java face, growing with every stage from stage 3: `Optional` requests and whatever else the Java conformance runner and the Java usage tests find awkward | nothing more |
  | `itinera-testing` | Test support, chapter 8, added by an application to its tests only, as chapter 8, 8.1 point 2 asks, with its asynchronous parts usable only with `itinera-kotlin` | `itinera`, and `itinera-kotlin` as an optional dependency (`compileOnly`, and `requires static` in its module descriptor), so a Java application's tests do not bring it |
  | `itinera-bom` | The versions of the artifacts above, so an application names the version once | |
  | `itinera-checker` | The rules that turn annotation mistakes into compile errors (decision 4), with a KSP processor for Kotlin and a javac annotation processor for Java over them, which an application adds with a build line or two, applying the KSP Gradle plugin as well in Kotlin | nothing at run time: a processor runs only in the compiler |

  Two unpublished projects, `conformance` for Kotlin and `conformance-java` for Java, hold the conformance runners and their fixtures.
- **How the layers plug in.** The core reads classes through an interface, with a reader for classes written in Java built in; `itinera-kotlin` provides the reader for Kotlin classes and the walk for data classes through `java.util.ServiceLoader`, so adding the artifact is all an application does; on the module path, the core's module descriptor declares `uses` and `itinera-kotlin`'s declares `provides`. The engine's cancellation check, `ensureActive()`, belongs to kotlinx.coroutines, so it too sits behind an interface that `AsyncLocalExecutor` fills; the synchronous engine needs nothing from kotlinx.coroutines, since `suspend` functions and `startCoroutine` are in the standard library.
- **Dependencies, and why.** Each has its reason in the tech spec that adds it. `kotlin-reflect` is about 3 MB; whether `kotlin-metadata-jvm`, which reads the same facts from the class's metadata without the rest, can replace it is for the first tech spec that adds it, in stage 1, where copying data classes needs it. No other library is needed: values need none of their own (section 2), and `TypeToken` is a few lines, against Guava's 3 MB.
- **Packages follow concepts**, named with the specification's vocabulary, as Rust's modules do: `error`, `value`, `journey`, `step`, `policy`, `event`, `report`, `request`, `service`, `workflow`, `instance` and `executor`, under one root (decision 8), plus the engine, which no application reaches. The JVM's module system refuses a package split across two artifacts, so each artifact's packages are its own: what an artifact adds to a concept lives in a subpackage of that concept's package named for the artifact's face, such as `executor.async` for `AsyncLocalExecutor` and `workflow.async` for `ItineraAsyncWorkflow` and the asynchronous builder, a `kotlin` subpackage of each concept the reified sugar extends, such as `value.kotlin` for `data.read<Long>` and `workflow.kotlin` for `builder<Orders>`, `java` subpackages for `itinera-java`, and `testing` for test support. Kotlin has no re-exports, so applications import each type from the package of its concept, as Rust's public paths read.
- **A Java module descriptor** in each artifact exports the public packages and not the engine's. Kotlin's `internal` does not cross Gradle modules, so what `itinera-kotlin` and `itinera-testing` call in the core, starting the engine and filling its reader and cancellation interfaces, is public Kotlin in packages of the engine, which the core's descriptor exports only to those modules, by qualified exports (`exports ... to ...`). An application on the module path cannot reach the engine; one on the class path can, and the documentation says the engine's packages are not API. An application on the module path `opens` its workflow and data packages to itinera, and, for its Kotlin classes, to `kotlin.reflect`, from which kotlin-reflect makes its reflective calls.

### 2. Values and the data bag

Decided by the maintainer on 2026-10-21 (decision 5): a value is the application's own object, checked, kept and read by its runtime type. Nothing is serialised, since chapter 2, 2.9 point 3 leaves serialising to reporters, and itinera has no use for a JSON tree.

- **A value**, as chapter 1, 1.3 defines it, is an object of one of these shapes, which itinera checks by its runtime class, part by part:
  1. `null`, a `Boolean`, a `String` or a `Char`;
  2. a number: `Byte`, `Short`, `Int`, `Long`, a finite `Float` or `Double`, or a `BigInteger` or `BigDecimal` of exactly that class, since both can be subclassed;
  3. an immutable value type of the JDK whose natural form is a string, such as `UUID`, and the dates, times and durations of `java.time`; the tech spec lists them;
  4. an enum constant, or, with `itinera-kotlin`, a Kotlin `data object`, whose fields are all final and hold immutable values: shared ones, finite numbers, other such constants and objects, and records and data classes holding only those, since every receiver shares the constant itself; an enum constant with a body of its own is recognised as an `Enum`, not by `Class.isEnum()`, which is false for it;
  5. a `List` or a `Set` of values, or a `Map` whose keys are strings and whose values are values;
  6. a JVM record whose components are values, whether a Java record or a `@JvmRecord` data class, or, with `itinera-kotlin`, a Kotlin data class whose only fields, its superclasses' included, are the `val` properties of its primary constructor, and hold values.

  Anything else is not a value: functions and lambdas, threads, streams, connections, arrays, a Kotlin value class, which the JVM boxes into a class of its own, and every other class, whose fields itinera cannot know to be data. The documentation says to make data a data class in Kotlin and a record in Java. Chapter 1, 1.3 counts "any type of the language that serializes to" a value, and each shape has an obvious form in those terms: a record or data class is an object of its components, a collection a list or an object, an enum constant or `data object` its name, and a JDK value type its standard string.
- **Why a walk of itinera's own.** Reuse came first, and three libraries that copy object graphs were tried on 2026-10-21, at their newest versions: Apache Fory 1.7.7, cloning 1.13.0 and Kryo 5.6.2. Verified:
  1. Fory, with class registration turned off, copied a data class and a record deeply, and refused a lambda, a `Thread` and a `Socket` through a list of classes it disallows, so it accepts any other class, the opposite of the check above. With registration on, its default, the application would register every class of its data with Fory. It is a serialisation framework of 2.7 MB and over 1,500 classes, of which itinera would use one method.
  2. cloning copied a data class but failed on a record, and accepted a `Socket`.
  3. Kryo copied a record shallowly, sharing its list, could not copy a data class without a constructor of no arguments, and accepted a lambda.

  None checks shapes, so itinera walks every object it captures anyway. The same walk makes the copy, with nothing but the JDK's collections, `java.lang.reflect.RecordComponent` and, for data classes, kotlin-reflect.
- **One walk copies a value.** It checks the object's shape and copies it:
  1. every list, set and map is copied, keeping its order and any `null`, into a fresh `ArrayList`, `LinkedHashSet` or `LinkedHashMap`;
  2. a record or data class is read through its fields, never its accessors, which an application may override, and rebuilt through its canonical or primary constructor with the copied components. What the constructor makes is the copy, even if it changes what it is given, which proposal 0121, point 4, calls the application's mistake: a record whose compact constructor writes `items = List.copyOf(items)` gives a copy holding a list that cannot be changed, which is the application's own choice of type;
  3. strings, numbers and the other immutable leaves are shared.

  Verified on 2026-10-21, with read-only collections in place of the changeable ones above: a data class holding a mutable list and a record holding another, copied this way, equal the original and do not change when it changes afterwards; a data class with a `var` property and a lambda are refused. Copying calls application code: constructors, `init` blocks, and the `equals` and `hashCode` of a set's elements and a map's keys.
- **A private copy when captured, a fresh copy for each receiver**, as proposal 0121 requires, chapter 4, 4.7 point 4 and 5.10. At every point where something enters a journey, initial data, contributions, event data, a reason's details, global metadata, an adapter's value and a provider's data, the walk checks the object and copies it into a copy that only itinera holds. Every receiver, each request, each typed read and each read through an input adapter's access to the data bag, gets a fresh copy of that, which it may change, where its types allow, without changing the data bag or what any other receiver gets: the case of proposal 0027 in which a step changes its input expects the step and the journey to succeed. Reporters and the result are not receivers in the sense of chapter 4, 4.7, and chapter 4, 4.7 point 4 allows a copy that calls application code only at capture, for a request and for a read through an adapter's access, so reporters get the event's own captured copy, and the result hands over the data bag's own copies once the journey is over; the documentation says a reporter must not change event data. A copy that fails while a value is captured makes it not a value, and one that fails while a value is read makes it of the wrong type for that request, as chapter 5, 5.10 now lists; for a read through an adapter's access, the adapter is told the value is of another type, and nothing is emitted. The abort or refusal carries the error, as a diagnostic.
- **Reads check the runtime type.** A request, or a typed read of the data bag, names the type it wants, generics included. The value is of that type when it is an instance of it, as Java's `instanceof` says, with every element of a list or set, and every value of a map, checked against the type's arguments, since the JVM erases them, and every component of a generic record or data class checked against its declared type with the request's arguments put in. A `null`, as the value or as an element, is of a Kotlin type only when that type is nullable, `Long?` or `List<Long?>`, and of a reference type read from a Java class unless JSpecify marks that type as excluding it (below); it is never of a Java primitive such as `long`. Otherwise the value is `wrong type`, with no error, since no custom code ran. Nothing converts, not even between numbers: an `Int` read as a `Long` is `wrong type`, as an `i32` read as an `i64` is in Rust, so an application writes `40L` where a `Long` is read. Verified: a Kotlin parameter of type `List<Long>`, and a Java one, accept `[1L, 2L]` and refuse `[1, 2]` and `["a"]`; a `Map<String, Order>` accepts a map of records and refuses a map of numbers; a stored `Long` reads into a Java `long`; a stored `Int` does not read as a `Long`; kotlin-reflect tells a `List<Long?>` from a `List<Long>`.
- **What a request may name.** Any type a value can be an instance of: one of the shapes above, or a supertype such as `Collection`, `Number`, `Any` or a sealed interface, sealed class or abstract class of the application's with no fields of its own, whose members are records or data classes. Since a receiver's copy holds `ArrayList`, `LinkedHashSet` and `LinkedHashMap`, a request may also name Kotlin's `MutableList`, `MutableSet` and `MutableMap`, or those three classes. A type no value can be is refused when the workflow is described: any other concrete collection class, such as `LinkedList`; an array; a map whose keys are not strings; and a class that is not one of the shapes. The tech spec of stage 1 settles the list.
- **`null` and optional requests.** A stored `null` is a value: read into a type that is not nullable, or into a Java primitive, it is `wrong type`, and into a nullable one it gives `null`. A primitive parameter is always required. An optional request whose own type admits `null` cannot tell a stored `null` from an absent key, so, as Rust's macros do, such a request is written `required` when it means "present, possibly null" (section 4).
- **Java's nullability through JSpecify** (decision 15). Java's types cannot say that `null` is excluded, so itinera reads the annotations of [JSpecify](https://jspecify.dev/) 1.0, the standard that Spring Framework 7 and the Kotlin compiler read. In code within `@NullMarked`, on the method or constructor, the class, an enclosing class, the package or the module, as JSpecify defines it, and not within `@NullUnmarked`, a reference type not marked `@Nullable` excludes `null`, at the top and in each type argument, as a Kotlin type that is not nullable does: a stored `null` read into it is `wrong type`. A type marked `@NonNull` excludes `null` in any code. Type variables and wildcards follow JSpecify's own rules for them, which the tech spec of stage 1 sets out. Code that is not marked keeps the rule above, so every reference type admits `null`, and the documentation recommends marking. `@Nullable` says only that `null` is of the type; whether a Java request is optional is still said by `Optional<T>` (section 4), and since an `Optional` cannot hold `null`, a stored `null` read into an `Optional<T>` request is `wrong type`, in marked code or not. A Java request that means "present, possibly null" is a required parameter of a type that admits `null`: `@Nullable T` in marked code, any reference type otherwise, the counterpart of Kotlin's `required = true` on a `String?`. The readers match the annotations by their names, so the core gains no dependency, and an application that marks its code already has JSpecify's jar. The tech spec of stage 1 says how far the rule reaches into the components of a Java record, and stage 4's tech spec covers parameters.
- **Initial data never makes `create()` throw.** `create()` captures the initial data, so the ID generator reads it, but a key whose object is not a value, or whose copy fails, is only recorded on the instance, and `run` refuses it, listing every such key, as chapter 5, 5.1 points 2 and 3 require; the same holds for initial global metadata. Initial data given as a record or a data class is split into keys by reading its fields, which calls no application code.
- **The data bag** maps `String` keys to values, keeping keys in the order they were first set. A typed read, `data.read("amount", TypeToken.of(Long::class.javaObjectType))`, or `data.read<Long>("amount")` with `itinera-kotlin`, returns a `Read`: present with the value, absent, or of another type, as chapter 4, 4.2 point 8.3 requires an adapter to be told.
- **No library in the API.** Itinera's public signatures type a value as `Any?`, `Object` in Java. A reporter that writes JSON serialises event data with the library it chooses, configured for records, data classes and `java.time` as that library needs.

### 3. Value conversions: not claimed

This plan raised the question as spec#121, and the specification answered it with proposal 0121, accepted on 2026-10-27:

1. code the application supplies that the implementation calls only to copy a value, keeping its type and its content, such as a record's constructor or a set element's `equals` and `hashCode`, is not a value conversion, so this plan does not claim `value-conversions`, does not list proposal 0113 or run the cases tagged `@capability-value-conversions`, and still claims tier 1;
2. a copy that calls application code is made for each receiver, and must not be shared in a way that turns a change into a failure, which rules out the shared frozen copy this plan first chose (section 2);
3. a copy that fails while a value is captured makes it not a value, and one that fails while a value is read makes it of the wrong type for that request;
4. a copy whose content differs from its original is the application's mistake, which itinera does not detect.

Proposal 0121 adds no scenario: a language that copies through application code proves the two rows of 5.10 in its own tests, and its tech spec lists them. Stage 1 writes those tests, in Kotlin and in Java.

### 4. Requests and their types

A parameter's declared type survives compilation, generics included, and reflection reads it, so a request's type is simply its parameter's type: `@Input amount: Long` in Kotlin, `@Input("amount") long amount` in Java. Verified for both, including `List<Long>`, Kotlin's `String?` and Java's `Optional<String>`.

- **Required or optional.** A Kotlin parameter of a nullable type, `Long?`, is optional; with `itinera-java`, so is a parameter of type `Optional<T>` in a class written in Java. Anything else is required. A required request whose value may itself be `null` writes `required = true`, as in `@Input(required = true) note: String?`. The suggested names of chapter 4, 4.11 point 2 follow: a required request gives the value, an optional one its absence or the value.
- **Keys.** Each request's key is written in its annotation, or, when not written, is the parameter's name, as in Rust. Kotlin always keeps parameters' names in its `@Metadata`, which kotlin-reflect reads, though plain Java reflection shows `arg0` for them unless the class was compiled with `-java-parameters`; Java keeps them only when compiled with `-parameters`, which Spring Boot and Quarkus builds already turn on. A request with no written key whose name was not kept is refused when the workflow is described, saying to write the key or compile with `-parameters`.
- **Handles and facts by type.** As in Rust's macros, what a request's type alone identifies needs no annotation: `Contributor`, `StepReporter`, `HookReporter`, `ProviderReporter`, `JourneyId`, `StepName`, `Attempt`, `Reason`, `Throwable` for the error, the causes, and `DataBagAccess`. A reason or an error may be optional, as `Reason?`. What a type cannot say is marked, such as `@Key` on the `String` parameter that receives the key an input adapter is resolving.
- **The builder names types with tokens**, typed requests made once, usually as constants, and used to declare and to read, as in Rust: `Requests.input("amount", TypeToken.of(Long::class.javaObjectType))` or `Requests.optionalInput(...)` in the core, `Requests.input<Long>("amount")`, reified, with `itinera-kotlin`, and `JavaRequests.optionalInput(...)`, whose answer is an `Optional`, with `itinera-java`. The factories are an object of their own, `Requests` in `org.itineradev.itinera.request`, rather than static methods of the annotation `Input`: Kotlin allows such methods, but javac reads them as elements of the annotation and refuses every `@Input` that does not give them a value. Whether a request is required is said by which factory makes it, and whether a stored `null` is of its type by its token (rule 5 of "What keeps the core reachable from Java"). A token declares the request and reads its value, already of its type, so the builder cannot read a value as another type than it declared. Each request names the kinds of part that may make it, such as `ContributorKind` for the contributor, so a part reads only what its kind may request, at compile time.

### 5. The public API: interfaces and annotations

The maintainer's principle for TypeScript holds here: the annotation API is the one applications write, as close to Rust's macros as the language allows, and whatever the types can refuse does not compile. The design:

1. **Interfaces, not base classes.** An application's step implements `ItineraStep`, a rescue step `ItineraRescueStep`, a policy `ItineraStepPolicy` or `ItineraWorkflowPolicy`, and a workflow `ItineraWorkflow`, or `ItineraAsyncWorkflow` from `itinera-kotlin` (section 11). A class has one superclass, which is the application's to use; an interface takes none of it. The interfaces' default methods are the helpers Rust's macros generate: `succeed()`, `fail(reason)`, `skip()` and `skipBecause(reason)` on `ItineraStep`; `succeed()` and `fail(reason)` on `ItineraRescueStep`; `keepDefault()`, `failWorkflow(reason)` and `finishWorkflow()` on `ItineraStepPolicy`; `supply(value)`, `fromDataBag()`, `provide(service)` and `instance()` on both workflow interfaces. Each also exists as a static factory, such as `Outcome.success()`, for code outside such a class.
2. **Annotations record; reflection reads.** The annotations take the names of Rust's macros, such as `@Workflow`, `@Step`, `@RescueStep`, `@StepPolicy`, `@WorkflowPolicy` and `@Role`, and each interface whose name one of them needs carries the `Itinera` prefix, such as `ItineraWorkflow` and `ItineraStep`. Annotations mark a workflow's steps and policies, a method's hook kind, and each parameter's request. When a workflow is first described, itinera reads them by reflection into the same descriptors the builder makes, checks every violation of chapter 3, 3.6 at once, and caches the descriptor per class (section 6).
3. **Mistakes are refused before any journey.** What the types cannot check, because an annotation constrains nothing about the method it marks, is refused when the workflow is described, throwing `Violations` that list every problem: a hook whose return type is not its kind's, a request a hook's kind may not make, a role the workflow does not implement, a part of the other mode. `itinera-checker` also reports these as compile errors, in Kotlin through KSP and in Java through javac, for applications that add it (decision 4); without it they are refused when described.

#### The orders example of itinera-rs, in Kotlin

The same workflow as `crates/itinera/examples/orders.rs`, to show how close the two are. Names follow Rust's, in camelCase; packages are shortened to their concept.

```kotlin
import itinera.executor.LocalExecutor
import itinera.journey.Contributor
import itinera.journey.JourneyId
import itinera.policy.*
import itinera.service.Provided
import itinera.service.Provider
import itinera.service.Service
import itinera.step.*
import itinera.workflow.*

/** Takes payments: the service a charge is paid through. */
fun interface PaymentGateway { fun take(amount: Long): String }

/** The shop's card terminal, lent to one attempt to charge. */
class Terminal(private val shop: String, private val attempt: Attempt) : PaymentGateway {
    override fun take(amount: Long) = "$amount paid at the $shop terminal, attempt $attempt"
}

/** Charges the amount the workflow's pricing works out. A charge of nothing is declined. */
@Step
class Charge(@Input private val amount: Long) : ItineraStep {
    fun run(@Service payments: PaymentGateway, contributor: Contributor): Outcome {
        if (amount <= 0) return fail("declined")
        contributor.contribute("payment", payments.take(amount))
        contributor.contribute("charged", amount)
        return succeed()
    }
}

/** Ships the order. */
@Step
class Ship : ItineraStep {
    fun run(): Outcome = succeed()
}

/** Notes each amount charged. */
@StepPolicy(name = "audit")
class Audit : ItineraStepPolicy {
    @OnStepSuccess
    fun audited(@FromStep charged: Long, contributor: Contributor): OnSuccess {
        contributor.contribute("audit", "charged $charged")
        return keepDefault()
    }
}

/** A role the shop provides: telling a customer something. */
@Role
interface Messages { fun tell(message: String) }

/** Tells the customer once the order is paid and shipped. */
@WorkflowPolicy(name = "notify")
class Notify : ItineraWorkflowPolicy {
    @OnWorkflowSuccess
    fun paid(id: JourneyId, @FromWorkflow charged: Long, @FromWorkflow payment: String, @Role messages: Messages) {
        messages.tell("order $id: paid $charged, $payment")
    }
}

/** Prints each event of every journey. */
class Printer : Reporter {
    override fun report(event: Event) = println("${event.journeyId} ${event.kind}")
}

@Workflow(name = "orders", policies = [Notify::class], reporters = [Printer::class])
@WithStep(Charge::class, name = "charge", retryBudget = 1, policies = [Audit::class])
@WithStep(Ship::class, name = "ship")
class Orders(private val shop: String) : ItineraWorkflow, Messages {
    override fun tell(message: String) = println("$shop: $message")

    /** Works out the amount to charge: the price, less any discount. */
    @InputAdapter(steps = ["charge"])
    fun pricing(@FromWorkflow price: Long, @FromWorkflow discount: Long?): Supplied =
        supply(price - (discount ?: 0))

    /** Lends each attempt to charge the shop's card terminal. */
    @Provider(perAttempt = true, steps = ["charge"])
    fun payments(attempt: Attempt): Provided<PaymentGateway> = provide(Terminal(shop, attempt))

    /** Names each journey after the shop and the order. */
    @IdGenerator
    fun orderId(data: DataBag): String = "$shop-${data.read<String>("order").orNull() ?: "unknown"}"
}

fun main() {
    val executor = LocalExecutor()
    for (order in listOf(mapOf("order" to "1", "price" to 40L, "discount" to 5L), mapOf("order" to "2", "price" to 10L, "discount" to 10L))) {
        val result = executor.run(Orders("corner").instance().initialData(order).create())
        println("${result.journeyId} ${result.status}")
    }
}
```

The example leaves out its imports of `Reporter`, `Event`, `Role`, `DataBag` and `Supplied`. It writes `40L`, since a value is read by its exact type and an `Int` is not a `Long` (section 2).

The asynchronous version differs only in its modifiers: `class Orders(...) : ItineraAsyncWorkflow, Messages`, `suspend fun run(...)` on each step, `suspend` hooks, input adapters, providers and reporters, and `AsyncLocalExecutor().run(...)` called from a coroutine; the ID generator stays synchronous (section 10). Every other part of an asynchronous workflow is `suspend`, as section 11 says.

The Java version, which the core and `itinera-java` run from stage 3, reads the same with Java's syntax: `@Step public final class Charge implements ItineraStep` with `@Input("amount") long amount` in its constructor, `@WithStep(step = Charge.class, name = "charge", retryBudget = 1, policies = Audit.class)`, `Optional<Long>` where Kotlin writes `Long?`, and `new LocalExecutor().run(...)`.

### 6. The builder and the descriptors

- **The builder is the core**, as in Rust. `WorkflowDescriptor.builder(...)` makes a synchronous workflow, and `asyncBuilder(...)`, in `itinera-kotlin`, an asynchronous one. Each adds step descriptors, workflow policy descriptors, reporters, input adapters, service providers and an ID generator, and `build()` checks every violation of chapter 3, 3.6 that the types do not rule out, throwing `Violations` with all of them. Steps and hooks are given as factories over typed tokens, as Rust's `StepFactory` is: a step declares its requests, handles included, with `.request(AMOUNT)`, and its factory receives `got`, reads `got[AMOUNT]`, `got[PAYMENTS]` and `got[CONTRIBUTOR]`, where `CONTRIBUTOR` is `Requests.contributor()`, and returns the step's run: a `fun interface` in the synchronous builder, which a Java lambda fits, and a `suspend` function in the asynchronous builder, so neither builder can take a part of the other mode. Every hook kind has its own typed method, so a hook's lambda returns its kind's own type and requests only what its kind may, at compile time; a provider of journey scope gets a `got` with neither the step's name nor the attempt to read, and a provider's lambda returns a `Provided<T>`, never nullable, of which `noInstance()` is the "nothing at all" of chapter 4, 4.9 point 6.2; a `null` that Java code returns anyway is an unexpected result (section 11).
- **Annotations are read into the same descriptors.** `WorkflowDescriptor.of(Orders::class.java)` describes an annotated class: it reads the annotations, with the reader for Java classes or, for a Kotlin class, the one `itinera-kotlin` provides, builds factories that construct the step with its constructor and call `run` through reflection, and goes through the same `build()`. Its mode is the one of the workflow interface the class implements. It is cached per class, so the first `instance()` describes the class and every later one reuses it. A test that calls `WorkflowDescriptor.of` checks the declaration without running anything, and the documentation recommends one.
- **The descriptor is its own object**, beside the application's workflow object, as in Rust and itinera-ts decision 12. It calls the workflow's adapters, providers and ID generator with the workflow object, so they read its fields.
- **A hand-written descriptor runs too.** The interfaces the engine uses, `WorkflowDescriptor`, `StepDescriptor`, `PolicyDescriptor` and `WorkflowInstance`, are public, so any executor can run any instance however it was produced, as chapter 5, 5.9 point 2 requires. They are typed as the builder is, as itinera-ts types its descriptor interfaces: each carries its mode as a type parameter, `StepDescriptor<Sync>`, holding callers whose type depends on the mode, such as `StepRun<M>`: `SyncStepRun`, a `fun interface` in the core, and `AsyncStepRun`, with a `suspend` method, in `workflow.async` in `itinera-kotlin`, which adapts it to a `suspend` interface of the engine's, exported only to `itinera-kotlin`, so no asynchronous type is public in the core. A hook's caller returns its kind's own type, a rescue step's caller returns `RescueOutcome`, and a provider of journey scope receives nothing that holds the step's name or the attempt, so a hand-written descriptor cannot write what the builder cannot. Descriptors that `build()` made are known as checked; `run` checks any other for every violation before the journey, as chapter 3, 3.7 point 2 requires. Generics are erased, so an unchecked cast in Kotlin or a raw type in Java can still pass an instance of one mode as the other, as a cast can in TypeScript: each executor therefore compares the mode of the descriptor and of every part with its own before every journey, built or hand-written, which costs a walk of the step list, and refuses with `mode not accepted`.
- **The conformance runners use the builder**, each in its own language, as itinera-rs's runner does and as the cases' FORMAT.md asks: "using the language's public API for constructing workflows". Their fixtures drive hand-written annotated workflows through the cases' own sentences (section 15).

What is refused, and when:

| When | What |
|---|---|
| At compile time | With the builder: a hook returning what its kind may not, a request its kind may not make, a read with another type than its token declared, a rescue step's factory returning a skip, a provider of journey scope reading the step's name or the attempt, a part of the other mode, and a write through an adapter's access. In annotated code: a write through an adapter's access, which has no method that writes; `FinishWorkflow` from a hook declared to return `OnFailure`, and a skip from a rescue step's `run` declared to return `RescueOutcome`, since those types have no such member. Everywhere: an instance handed to the executor of the other mode, unless an unchecked cast hides its mode, which `run` refuses |
| When the workflow is described, before any instance | Every violation of chapter 3, 3.6, such as two steps with one name or an adapter for an unknown step; `role not provided`; and every mistake the annotations' types cannot catch: a hook, `run`, factory, input adapter, provider or ID generator whose declared return type is not its kind's, such as a failure hook declared to return `OnSuccess`, a Kotlin return type that admits `null`, such as `Outcome?`, `Supplied?`, `Provided<T>?` or an ID generator's `String?`, an ID generator declared to return anything but `String`, or a workflow hook declared to return anything but `Unit` or `void`; a provider of journey scope requesting the step's name or the attempt (`attempt request in journey scope`); a part whose mode is not the workflow's, such as a step without `suspend` in an `ItineraAsyncWorkflow`; an ID generator declared `suspend`, in either mode; a request its kind may not make, a parameter with no request, a key that cannot be found, a step class with no `run`, an annotation on a class that does not implement its interface, a request whose type no value can be, such as `LinkedList` or an array (section 2); and a Kotlin class without `itinera-kotlin`. With `itinera-checker`, the mistakes of annotated code among these are also compile errors (decision 4) |
| When `run` is called | initial data and initial global metadata that are not values, initial global metadata that sets `journey_id`, every violation of a hand-written descriptor, an instance whose mode is not the executor's, an instance that already ran, and a call while a journey runs |

### 7. Steps

- **Requests resolve in the order written**: the constructor's parameters, then `run`'s.
- **Built once per attempt**, by its constructor, which may throw (`step could not be built`). Nothing carries over between attempts.
- **Outcomes**: `succeed()`, `fail(reason)`, `skip()` and `skipBecause(reason)`, where a reason is a code alone or a `Reason` with a code, a message and details, as chapter 6, 6.11 point 2 suggests. `run` returns `Outcome`, and is a `suspend` function in an asynchronous workflow. Anything `run` throws is an abnormal termination, except the executor's signal and a `java.lang.Error` (section 11).
- **Handles belong to the attempt.** The contributor and the step reporter are made for the attempt and closed when it ends. A call on a closed handle runs nothing and throws `IllegalStateException` where it is made, as chapter 4, 4.6 point 7 says it should.
- **Handles in each mode.** A synchronous step's `StepReporter` blocks until every reporter has the event; an asynchronous step's `AsyncStepReporter` has `suspend` emits, which return once every reporter has it. A step requesting the handle of the other mode is refused when described. An emit is a call the step waits on, so events keep the order of the calls; an emit from a coroutine the step launched outside its own scope, which outlives the attempt, meets a closed handle.
- **The executor's signal.** The engine records the abort, then the call that caused it throws the journey-abort exception, a private class no application can name, carrying the abort reason and the error. Since the abort was recorded first, a step that catches it, as `catch (e: Exception)` would, still ends the journey aborted, with no outcome fact and no commit.
- **Rescue steps** implement `ItineraRescueStep`, whose `run` returns `RescueOutcome`, which has only success and failure.

### 8. Policies, hooks and roles

- **Two kinds of policy**, classes implementing `ItineraStepPolicy` or `ItineraWorkflowPolicy`, each with a constructor of no arguments, which may throw: workflow policies are built once per journey, before the dispatcher (a failure is a refusal), step policies for every attempt (a failure aborts with `policy could not be built`). The JVM cannot make an instance read-only inside a hook, so rebuilding is what keeps any change from outliving the attempt or the journey, as chapter 6, 6.1 point 7 allows.
- **Each hook returns its own type**: `OnSuccess` for `on step success` (`keepDefault()`, `finishWorkflow()`, `failWorkflow(reason)`), `OnFailure` for the three failure hooks (`keepDefault()`, `failWorkflow(reason)`), and nothing for workflow hooks, as chapter 6, 6.11 suggests. Both are sealed, so `FinishWorkflow` cannot be an `OnFailure`. A step hook keeps the default only by returning `keepDefault()`, the one form of nothing that chapter 6, 6.3 point 1 and proposal 0122 ask for; a `null`, which Java allows, is an unexpected result (section 11). Workflow hooks are void, `Unit` in Kotlin and `void` in Java: an annotated workflow hook declared to return anything else is refused when described, and the builder's takes a function that returns nothing, so what a workflow hook returns is never read, and the cases' sentence for a workflow hook returning a value falls back to nothing in both runners. A hook is `suspend` in an asynchronous workflow. A hook fails by throwing, `hook failed`.
- **Requests** are marked as section 4 says; what a hook's kind may not request is refused when described.
- **Roles** are interfaces marked `@Role`, implemented by the workflow class. A hook requests one with a parameter marked `@Role`, and gets a `java.lang.reflect.Proxy` implementing only that interface and forwarding to the workflow object, so it cannot cast its way to the workflow as a whole, which chapter 6, 6.8 point 3 forbids. A policy attached to a workflow class that does not implement a role one of its hooks requests is `role not provided`, found when the workflow is described or built, and that scenario runs. A role operation that throws ends the hook with `hook failed`.

### 9. Workflow declarations

- **Each step states everything**: a retry budget (0 unless set, a non-negative `Int`, checked when declared), whether abnormal terminations are retried, its policies in order, and its rescue step.
- **Names** are non-empty strings, checked when made, held in small final classes, `WorkflowName`, `StepName`, `PolicyName`, `AdapterName` and `ProviderName`, made with `StepName.of("charge")`, so a plain string is not mistaken for one.
- **Input adapters** are methods of the workflow class marked `@InputAdapter`, requesting the step's name, the key, data from the workflow, the journey ID and `DataBagAccess`, returning `supply(value)` or `fromDataBag()`, the one form of the nothing of chapter 4, 4.2 point 3.1. `supply(null)` supplies the value null, checked against the input's type like any other value; a `null` instead of a `Supplied`, which Java allows, is an unexpected result (section 11). `DataBagAccess` has no method that writes, and shows nothing once its call has returned.
- **Service providers** are methods marked `@Provider`, returning `Provided<T>` made by `provide(instance)`, `provide(instance, data)` or `noInstance()`, the one form of the "nothing at all" of chapter 4, 4.9 point 6.2. The service's type is `T`, read from the method's generic return type, and `wrong service type` compares it with the step's parameter type. `noInstance()` gives `service_provider_failed`, then the journey aborted with `step could not be built`; a `null`, which Java allows, is an unexpected result (section 11), and a provider declared to return `Provided<T>?` is refused when described. The implementation `service_provided` names is the instance's class name, as chapter 4, 4.9 point 6.3 asks; the tech spec says which form of it, and that obfuscators rename classes. An instance made from a lambda, such as a `fun interface` service written as one, has a hidden class whose name changes from run to run, which is "an object with no class of its own" in that point's words: its implementation is the service type the provider declares, and the tech spec records it.
- **The listing**, `WorkflowDescriptor.listing()`, gives each step's name, position, policies, input adapter, services with their providers, and rescue section.

### 10. The workflow instance

- **`orders.instance()`**, a default method of both workflow interfaces, describes the class if it was not yet, and returns a builder: `.data(key, value)`, `.initialData(...)` with a map, a record or a data class, `.reporter(r)`, `.reporter { journeyId -> r }`, `.reportersGlobalMetadata(key, value)`, and `.create()`, which captures the initial data (section 2), then produces the journey ID, from the ID generator or a UUID version 4, then the reporters, as chapter 5, 5.1 orders them. `descriptor.instance(orders)` does the same for a descriptor the builder made. The ID generator and the reporter factories are synchronous in both modes, as in itinera-rs and itinera-ts, so `create()` is an ordinary function in both (decision 2, revised 2026-10-27): an asynchronous application that needs I/O to make the ID awaits it in its own coroutine first and puts the result in the initial data, from which the generator reads it. An ID generator declared `suspend` is refused when described, and the asynchronous builder takes the ID generator and the reporter factories as plain `fun interface`s, so a `suspend` one does not compile there.
- **The journey ID is a non-empty string**, as chapter 5, 5.2 and proposal 0122 require: `JourneyId.of` refuses an empty string, and an ID generator that returns `null` or an empty string, which Java allows, or that throws, makes `create()` throw `IllegalStateException`, saying what was returned, with no journey and no event, as for any other failure while the instance is created (chapter 5, 5.1 point 1). The same holds for a reporter factory that returns `null`. Kotlin's types rule out a generator returning anything but a `String`, so the Kotlin manifest lists `non-string-journey-id` as impossible; the Java runner runs it, and both run `empty-journey-id`.
- **The instance carries its mode in its type**: `WorkflowInstance<Sync>` from an `ItineraWorkflow` or the synchronous builder, `WorkflowInstance<Async>` from an `ItineraAsyncWorkflow` or the asynchronous builder. The executor relies on that one interface, holding the descriptor and the workflow object side by side, then the initial data, the journey ID, the reporters and the initial global metadata.
- **An instance runs once.** Running it again is refused.

### 11. The executors and the engine

- **One mode per workflow, two executors** (decision 2), as in itinera-rs. A workflow is all synchronous or all `suspend`: its steps, rescue steps, hooks, providers, adapters and reporters. The ID generator and the reporter factories are synchronous in both modes, since `create()`, an ordinary function, calls them while the instance is created (section 10). `LocalExecutor.run(instance: WorkflowInstance<Sync>)`, in the core, runs a synchronous workflow and returns the result; `AsyncLocalExecutor`'s `suspend fun run(instance: WorkflowInstance<Async>)`, in `itinera-kotlin`, runs an asynchronous one. Handing an instance to the executor of the other mode does not compile, and is refused with `mode not accepted` if an unchecked cast hides it (section 6), and a part of the other mode inside a workflow is refused when it is described or built, so no synchronous part ever blocks an asynchronous executor's thread. Whether a part's mode is right is read from the declaration: by the Kotlin reader in `itinera-kotlin`, through `KFunction.isSuspend` (verified), since a method of a Java class is always synchronous; what a `suspend` function does inside cannot be checked, as in Rust, and the documentation says a blocking call belongs in `withContext(Dispatchers.IO)`.
- **One engine**, in the core, written once as `suspend` functions, as Rust's is written once as asynchronous code. `LocalExecutor` starts it with a plain continuation and no dispatcher: a synchronous workflow never suspends, so it runs straight through on the caller's thread. Verified: a `suspend` engine started with `startCoroutine` and an empty context completes before the call returns. Since a synchronous workflow has no `suspend` part, and `run` checks the mode first, a suspension there can only be a bug in itinera, and the driver throws an `AssertionError`, an `Error` that reaches whoever called `run`, as a bug's panic does in itinera-rs.
- **The engine never spawns, sleeps, sets timers or cancels.** It awaits only what the workflow's own parts do. `AsyncLocalExecutor.run` runs in the caller's coroutine context, so on whatever dispatcher the caller uses, virtual threads included; itinera never chooses a thread.
- **`run` returns the result, or throws `Refusal`** before any journey, naming what refused it and carrying the error that caused it. Nothing that happens inside a journey escapes `run`, except a `java.lang.Error`, as "What is caught" says.
- **Before the journey**, in this order, as in itinera-ts: refuse an instance that ran, or a call while a journey runs; then make one admission check, refused with every violation it finds at once, as chapter 3, 3.7 point 3 requires: the violations of a descriptor that `build()` did not make, `mode not accepted` among them, an instance or part whose mode is not the executor's, whatever made it, the keys of initial data and initial global metadata that `create()` recorded as not values, and initial global metadata that sets `journey_id`; then, one after another, build the workflow policies; create the dispatcher and add the guarded reporters; set `journey_id`, then the initial global metadata, before `journey_started`. A failure in any of these is a `Refusal` with no event, as the first rows of chapter 5, 5.10 say for the dispatcher factory, the dispatcher, the reporters receiving the initial global metadata and the workflow policies.
- **Unexpected results** (proposal 0122). Every call into custom code is void or has a result, and the tech spec of each stage lists every call it adds with its shape, in Kotlin and in Java, and its form of nothing, as proposal 0122 point 1 requires. Reporters, a dispatcher while it adds reporters or delivers an event, role operations and workflow hooks are void: `Unit` in Kotlin, `void` in Java, and what they return is never read. Every other call has a result, and where it may return nothing, that nothing is `keepDefault()`, `fromDataBag()` or `noInstance()`, never `null`. The engine checks every result, though Kotlin's types rule the wrong ones out, since a Java class or a Java lambda can reach any workflow and Kotlin does not check what it returns. A `null` where a result is owed, from a step's or rescue step's `run`, a step hook, a step's or rescue step's factory, a step policy's construction, an input adapter or a service provider, aborts the journey with `unexpected result`, naming the code that returned it and the key where there is one. It is neither an outcome nor an abnormal termination, so it is never retried, and the abort carries a message saying what was returned. Before the journey, a `null` from the dispatcher factory or a workflow policy's construction is a `Refusal` naming it. A malformed result, such as a failure without a code, cannot be made: `fail`, `Reason.of` and the other factories check their arguments, and the `NullPointerException` they throw from Java, inside the custom code, is a throw, with the meaning chapter 5, 5.10 gives it; the tech spec of 0122 records this reading.
- **One journey at a time.** A call to `run` while the executor's journey runs is refused before anything starts; parallelism comes from several executors.
- **What is caught.** Every `Throwable` from custom code is caught except `java.lang.Error` and its subclasses, which propagate to whoever called `run`, as the last point of chapter 5, 5.10 says. Reflection wraps what a method throws in `InvocationTargetException`, kotlin-reflect's calls included, so the engine unwraps it before deciding, and carries the method's own error and message. That includes Kotlin's `TODO()`, which throws `NotImplementedError`, an `Error`; the documentation says so. A `CancellationException` abandons the journey only when the coroutine running `AsyncLocalExecutor.run` was cancelled, which the engine asks through the cancellation interface that `AsyncLocalExecutor` fills with `ensureActive()`; as Rust's dropped future, nothing more is emitted. Any other `CancellationException`, such as the `TimeoutCancellationException` of a step's own `withTimeout`, which chapter 4, 4.8 point 3 encourages, is custom code failing like any other: an abnormal termination from a step, `hook failed` from a hook.
- **One wrapper** around every call into a hook, a role operation, a reporter or a dispatcher while the journey runs, as itinera-ts decision 13: it records the abort with the call site's reason, unless one is already recorded, and throws the journey-abort exception, which the engine catches only where it runs the journey.
- **Inside the engine**, the same seams as Rust: the scan, a pure decision function, the step and hook callers, request resolution, services with journey-scoped instances kept until the journey ends, the rescue, the emitter with its replaceable clock, guards around reporters, and a runner seam that scripted runs replace.

### 12. Events, reporters and dispatchers

- **`Event` is a sealed interface**, one `@JvmRecord` data class per kind, each carrying its fixed fields: the sequence number from 1, the timestamp as an `Instant` that prints as ISO 8601 in UTC, the journey ID, the workflow name, and its kind's fields. `kind` is an `EventKind` enum whose members print as the snake_case names of chapter 2 and parse back from them, as chapter 2, 2.13 suggests. No engine event has a field that can hold a data bag value. Event data is the event's captured copy of the value, typed `Any?`, which every reporter receives (section 2).
- **Reporters**: `Reporter`, in the core, with `report(event)` and `setGlobalMetadata(key, value)`, which does nothing by default, for synchronous workflows; `AsyncReporter`, in `itinera-kotlin`, with the same methods as `suspend` functions, for asynchronous ones. `DebugReporter` prints each event, as Rust's does, and exists in each mode.
- **Dispatchers and their factories** follow chapter 2, 2.2, one kind per mode; `DefaultDispatcher` calls reporters in the order added. The executor wraps each reporter in a guard, so the rules of 2.3 hold whatever the dispatcher.

### 13. The result and errors

- **`JourneyResult`**, a `@JvmRecord` data class, carries the journey ID and a sealed `JourneyStatus`: `Succeeded` with the data bag, `Failed` with the failure and the data bag, `Aborted` with the abort and no data bag. `isSucceeded`, `isFailed`, `isAborted`, `failure` and `abort` read it without a `when` or `switch`, as chapter 5, 5.14 suggests.
- **A failure** carries its cause, reason and error; **an abort** its reason, details and error, as chapter 5, 5.8 lists. The abort reasons are an enum, `unexpected result` among them, whose abort also carries the message saying what was returned (section 11). The result holds the `Throwable` itself and its message; a `message` that is `null` or whose reading throws gives a fixed text, since nothing may escape `run`.
- **`Violations`**, **`Refusal`** and **`TestMistake`** are exceptions; `Violations` and `TestMistake` are unchecked, since they report declaration and test mistakes, and `Refusal` is checked in Java's eyes through `@Throws`, so a Java caller of `run` handles it.

### 14. Test support (`itinera-testing`)

The five parts of chapter 8, with its suggested names in camelCase: `RecordingReporter` with `events`, `globalMetadata` and `path`; `fakeProvider`, on a test instance builder that `itinera-testing` makes from a workflow object, with the same synchronous `create()` (section 10); `scripted()` with `step`, `andStep`, `onAttempt`, `onEveryAttempt`, `onRemainingAttempts`, `willContribute`, `willEmit`, `willSetGlobalMetadata`, `willSucceed`, `willFail`, `willSkip`, `willSkipBecause`, `willTerminateAbnormally`, `willRunForReal`, `ensureAllScripted` and `run`, with the record's `attempts`, `attempt` and `input`; the `Ending` a scripted attempt plays; and the recorders `Contributions`, `StepEventReporter`, `HookEventReporter` and a data bag built `with` values. A scripted run runs on the executor of the workflow's mode, as chapter 8, 8.5 point 9 says. A mistake in a test throws a `TestMistake` naming each problem. Its synchronous parts follow the core's five rules: its step mock, which the Java runner builds its workflows from, is reachable from Java from stage 3, and the rest of test support from stage 10. As in itinera-ts, the runners' scripted steps and policies are test support's own mocks, so conformance and test support are one harness, and they live in `itinera-testing` from the start, which both runners depend on, with their API marked experimental until 0108 is listed.

## Rules made impossible, and rules enforced at run time

Each exclusion has a proof in each language, since each manifest lists it and chapter 3, 3.8 point 2 asks every language to prove what it excludes: for Kotlin, a snippet compiled with kotlin-compile-testing, expected to fail, beside a twin that compiles; for Java, the same with `javax.tools`, in `itinera-java`'s tests; and, for those excluded by signature, a test in each language that the annotated form is refused when the workflow is described. In Java, `invalid-lifecycle` and `rescue-skip` are proven by javac refusing a class that implements `OnFailure` or `RescueOutcome`, and `mode-not-accepted` by javac refusing a call of `AsyncLocalExecutor.run`, with `LocalExecutor.run` as the twin, and by a Java class implementing `ItineraAsyncWorkflow` with a synchronous step being refused when described, since Java cannot write a `suspend` part at all.

| Tag | What cannot be written |
|---|---|
| `attempt-fraction` | an attempt number that is not whole: test support takes an `Int` |
| `bag-write` | a write through an adapter's access: `DataBagAccess` has no method that writes, in annotated code or with the builder, in Kotlin or in Java |
| `invalid-lifecycle`, by signature | with the builder, a failure hook returning `FinishWorkflow`: its lambda returns `OnFailure`, which is sealed and has no such member. Annotated code can still write `@OnStepFailure fun f(): OnSuccess = finishWorkflow()`, since an annotation constrains nothing about the method it marks; it is refused when the workflow is described, before any instance |
| `rescue-skip`, by signature | with the builder, a rescue step that skips: its factory returns `RescueOutcome`, which has no skip. Annotated code can still declare a rescue step's `run` as returning `Outcome` and return a skip; it is refused when described |
| `journey-scope-request`, by signature | with the builder and the descriptor interfaces, a provider of journey scope reading the step's name or the attempt: its `got` has neither. Annotated code can still request `StepName` or `Attempt` in a provider of journey scope; it is refused when described |
| `mode-not-accepted`, by signature | an instance handed to the executor of the other mode, since the instance's type carries its mode; with the builder and the descriptor interfaces, a part of the other mode, since each takes only functions of its own mode. Annotated code can still put a step without `suspend` in an `ItineraAsyncWorkflow`, or a `suspend` hook in an `ItineraWorkflow`; it is refused when described. Only an unchecked cast, which no typed code writes, can hide an instance's mode, and `run` refuses it then (section 6) |

The exclusions by signature rest on reading "through its types or signatures" in chapter 3, 3.8 point 1 as covering a signature itinera checks before any instance exists, since the runners, which use the builder, cannot express their scenarios at all. `invalid-lifecycle` and `rescue-skip` hold for Java code too: `OnFailure` and `RescueOutcome` are sealed interfaces whose `PermittedSubclasses` attribute javac and the JVM both enforce, so no Java class can be one (verified, rule 4 of "What keeps the core reachable from Java"). The maintainer chose this reading (decision 11); `itinera-checker` turns the annotated cases into compile errors for applications that apply it, and not for those that do not (decision 4).

The others run:

| Tag | How itinera-j enforces it |
|---|---|
| `role-not-provided` | the violation `role not provided`, found when the workflow is described or built: an annotation's array of policy classes cannot be tied to the workflow's type, and a policy requesting several roles cannot be typed against the workflow's, so the builder checks the same rule when it builds, and the scenario runs |
| `non-value` | the value check at every entry point (section 2), since a value's type is `Any?` |
| `late-handle` | handles closed when their attempt, hook or call ends; an object can always escape on the JVM |
| `no-instance` | a provider returning `noInstance()`, the explicit nothing proposal 0122 asks for: `service_provider_failed`, then `step could not be built`, as chapter 4, 4.9 point 6.2 says, in both runners |
| `unexpected-result`, `non-string-journey-id` | in the Java runner only: a `null` returned where a result is required aborts with `unexpected result`, and an ID generator returning `null` makes `create()` throw (sections 10 and 11). The Kotlin manifest lists both as impossible, by types and by signature: compile-fail tests for the builder and the descriptor interfaces, and tests that annotated code declaring a return type that admits `null`, or an ID generator returning anything but `String`, is refused when described; the engine still checks every result, since a Java class can reach a Kotlin workflow. Rust and TypeScript claim both as impossible too, since [itinera-rs#186](https://github.com/itinera-dev/itinera-rs/issues/186) and [itinera-ts#83](https://github.com/itinera-dev/itinera-ts/issues/83) |
| `empty-journey-id`, `attempt-zero`, `attempt-negative` | an empty journey ID makes `create()` throw; an attempt number of 0 or below, which an `Int` can hold, is a test mistake when a script describes it, and reading attempt 0 of a scripted run's record reads nothing, as chapter 8, 8.5 point 9 says |

The two tags of test support, `undeclared-handles` and `fake-service-type`, are enforced at run time by the mistakes `no contributor`, `no reporter` and `another service`.

One rule that chapter 3, 3.8 point 1, item 5, lists with the late handles cannot be enforced on the JVM, and no scenario checks it: a step keeping a service after its attempt. Chapter 4, 4.9 point 8.1 allows that, since the executor never lends the service again; the documentation says not to keep one.

## Testing

### 15. The conformance runners

- **Two runners, one per language** (decision 14). The `conformance` project, written in Kotlin and run with `./gradlew :conformance:run`, proves the Kotlin claim; the `conformance-java` project, written wholly in Java and run with `./gradlew :conformance-java:run`, proves the Java claim. Both run on Cucumber-JVM, as the cases' FORMAT.md names it for Kotlin and Java, read `ITINERA_CONFORMANCE_CASES`, `ITINERA_CONFORMANCE_TAGS` and `ITINERA_CONFORMANCE_REPORT`, write one Cucumber JSON report each, the Kotlin one checked against `conformance.json` and the Java one against `conformance-java.json`, and fail when a selected scenario fails or uses an undefined sentence. They share no code but itinera's own artifacts, test support's mocks among them, and the JSON library that parses the cases, Jackson 3 (`tools.jackson.core:jackson-databind`), which only the runners use. Cucumber-JVM 8's `json` plugin, now built on Cucumber's standalone JSON formatter over its messages, writes the report the `run-conformance` action reads, as stage 2 checked.
- **Only the public API.** In each runner, Given sentences fill a plain scenario model of its own, and "When the workflow runs" builds the scenario's workflow with that language's builder, from test support's mocks. Step statuses are derived from the events.
- **The Kotlin runner's two columns.** Each scenario runs as synchronous Kotlin on `LocalExecutor` and as asynchronous Kotlin on `AsyncLocalExecutor`, and a scenario tagged with one mode runs only in the column of that mode. Both columns write the Kotlin report. Cucumber-JVM has no supported way to copy a scenario per column, so the runner runs Cucumber once for each column, over the same cases, and merges the two JSON reports into one (stage 2's choice). Each run takes the sentences and the column's own glue, whose first hook tells the scenario which column it runs in, and a tag expression that leaves out the scenarios of the other mode, `@capability-async` in the synchronous column and `@capability-sync` in the asynchronous one. In the merged report, each feature lists the synchronous column's scenarios, then the asynchronous column's, each tagged `@executor-local` or `@executor-async`, so a scenario that ran in both appears twice. As in the Rust runner, the two copies are the rows of an Examples table the runner adds, each with a line of its own, since the Cucumber JSON report tells scenarios apart by name and line: the first copy keeps the scenario's line, and the second is moved past every scenario of the feature sharing its name, such as the rows of a Scenario Outline. The run fails when either column fails. When Android support lands, the Kotlin runner also runs on ART, as instrumented tests on an Android emulator in CI, with its own report.
- **The Java runner** is a plain Java project, compiled at release 17 against `itinera-java` and `itinera-testing`, with no Kotlin source: its step definitions, its scenario model, the code that builds each workflow through the Java API, and the code that reads the result, the events and global metadata through Java's own reading API, such as `isSucceeded()` on the result and `instanceof` patterns over events, are all Java. It runs synchronous scenarios on `LocalExecutor`. So conformance proves the whole of Java's API, as the cases' FORMAT.md asks of a language's runner, and Java 21's record patterns over events are left to the Java usage tests (section 16). Each runner holds a step definition for every sentence of STEPS.md, as the cases' FORMAT.md asks of a runner, and a test of each runner checks that none is missing, since a run fails on an undefined sentence only in the scenarios it selects. Each runner's test lands with the stage that defines its last sentence; until then, the sentences are added stage by stage, with the features that use them.
- **Fixtures**, the counterpart of Rust's `@macros` features, in `conformance/features/fixtures` and `conformance-java/features/fixtures`: workflows written by hand with the annotations, in Kotlin in both modes and in Java, from the stage that adds each feature, driven through the cases' own sentences, with a Given sentence naming each workflow, such as `Given the payment workflow`.
- **Values in the cases.** Each runner parses the cases' JSON with the same library, used only by the runners, keeping key order: an integer becomes a `Long`, any other number a `Double`, an object a `LinkedHashMap<String, Any?>` and an array a `List<Any?>`, and the cases' neutral type names map the same way, `integer` to `Long`, `number` to `Double`, `string` to `String`, `boolean` to `Boolean`, `list` to `List<Any?>` and `object` to `Map<String, Any?>`. Event data, global metadata and the result are compared with expected JSON parsed the same way. The Java runner maps them to the same Java types.
- **Changing received values.** The sentences of 0027 that change a received value in place do so "as far as the language allows", and do nothing where values cannot be changed, as the cases' STEPS.md says. Each receiver's copy can be changed, so the change succeeds and stays the receiver's own, as the case of proposal 0027 expects (proposal 0121).
- **Kotlin and Java stay compatible** (the maintainer, 2026-10-27). Two runners must never let the languages drift apart, so four rules hold from stage 3:
  1. **Same cases, same proposals.** A test in the root Gradle build, its own CI job, compares `conformance.json` with `conformance-java.json` field by field and fails unless all of these hold: `cases` is equal; `proposals` are equal as sets; Kotlin's `capabilities` are Java's plus `async`, which only Kotlin claims; under `impossible`, Java's tags are Kotlin's without `unexpected-result` and `non-string-journey-id`, which Java never lists and Kotlin may list or not, so stage 0's empty manifests pass; and each shared tag lists the same scenarios, by `feature` and `scenario`, while `proof` is not compared, since each manifest names its own language's test.
  2. **Both runners on every pull request**, each a required check, so nothing merges unless both languages pass.
  3. **A feature lands in both languages in the same pull request**: its Kotlin API and, where Java has it, its Java API, its sentences in both runners, and its fixtures in both. Asynchronous features have no Java API and their scenarios do not run in the Java runner, which does not claim `async`, but the Java runner still defines their sentences, as the cases' FORMAT.md asks of every runner.
  4. **A release ships both or neither**: the release gate checks both manifests and attaches both reports.
- **Two languages in one repository.** The cases' FORMAT.md describes one manifest, `conformance.json`, and one runner per language repository, and its compatibility table reads one report per release. Stage 2 changed FORMAT.md, in [itinera-dev/conformance#100](https://github.com/itinera-dev/conformance/pull/100), so a repository may hold several languages, each with its own manifest, runner and report: a language's manifest is `conformance-<language>.json`, though one language may keep `conformance.json`, as Kotlin does here, and its report files carry its name, `cucumber-<language>.json` and `exclusions-<language>.json`, so a release carries both languages' reports side by side.
- **The `run-conformance` action** of itinera-dev/actions runs once per runner, each run with its own command and its own report, since the action writes an exclusions file beside each report. It read `conformance.json` by a fixed name, so stage 2 added two inputs, in [itinera-dev/actions#23](https://github.com/itinera-dev/actions/pull/23), released in v1.8.0: `manifest`, naming the manifest, and `language`, naming the report's files and its artifact, `conformance-report-<language>`. The Kotlin run gives `language: kotlin` and the default manifest; the Java run, from stage 3, gives `manifest: conformance-java.json` and `language: java`.

### 16. Kotlin's and Java's own tests

- **Unit tests** with JUnit Jupiter, next to the code they check, named as sentences, with `@ParameterizedTest` named cases for one rule over several inputs, the counterpart of `rstest`.
- **Java usage tests of the core**, a source set of Java tests compiled at release 17 against `itinera` alone, from stage 3, exercising the synchronous API from Java, so a change that breaks one of the five rules fails a test even where `itinera-java` would hide it. A second source set, compiled with a JDK 21 toolchain and run in the JDK 21 and 25 jobs, covers what only Java 21 writes, such as record patterns over events. A Java compile-fail test, compiled with `itinera-kotlin` on its class path, shows that `AsyncLocalExecutor.run` cannot be called from Java.
- **Compile-fail tests**, the proofs and every refusal the builder's and executors' types make, in Kotlin with the maintained fork of kotlin-compile-testing, `dev.zacsweers.kctfork`, which supports the K2 compiler, and in Java with `javax.tools`, each with a twin that compiles.
- **Property-based tests** with Kotest's property testing or jqwik, as Rust's proptest ones: first and last events, increasing sequence numbers, one outcome fact per attempt, one decision per failed attempt, attempts within the budget, no data bag values in engine events, identical streams from a workflow run in both modes.
- **Documentation examples are real code**, compiled and run by the tests and pulled into KDoc with Dokka's `@sample`, so no example can rot.
- **The public API is recorded** with the Kotlin Gradle plugin's ABI validation, still experimental in Kotlin 2.4 but working, which stage 0 chose over the binary-compatibility-validator plugin it grew from (`checkKotlinAbi`, and `updateKotlinAbi` to write the dump): a dump of each artifact's public API is checked in, so every change to it shows in a pull request.

## Code rules for the agents' manual

The new AGENTS.md carries Rust's and TypeScript's rules over where they are not about the language:

- Names use the specification's vocabulary, in camelCase as proposal 0111 shows for Kotlin (`keepDefault`, `fromDataBag`, `isFirst`), and types in PascalCase.
- Types hold every constraint they can: name classes, an `Attempt` counted from 1 with `isFirst`, sealed interfaces for closed sets, a mode in the instance's type, `val` and read-only collections everywhere. A comment stating a constraint the type could enforce means the type is wrong.
- Kotlin's explicit API mode is on, and warnings are errors. The core's public API keeps the five rules of "What keeps the core reachable from Java", which are review items, and the Java usage tests check them.
- Reflection only in the annotation readers, the value walk and the lending of roles, behind interfaces, and in `TypeToken`'s one read of its superclass; the engine and the rest of the builder never use it, but to check what a class is marked or made as (decision 17).
- Nothing in the core uses kotlin-reflect or kotlinx.coroutines; they belong to `itinera-kotlin`.
- No throw escapes `run` while a journey runs; declarations may throw before a journey, with a message saying what was wrong.
- Packages follow concepts; a file past 200 lines holds one thing; tests sit beside their code.
- Closed sets of names are enums; data that varies by case is a sealed interface matched with an exhaustive `when`.
- Collection operations over loops that build a result, and chains that read as a sentence of named functions, as Rust's closure rule says.
- Reuse before writing: the JDK and Kotlin's standard library, then libraries already depended on, then well-known libraries; write it ourselves only when none fits. Every runtime dependency has a stated reason in the tech spec that adds it.
- As few comments as possible, never referring to specification sections, issues or pull requests; no `TODO`, in comments or as Kotlin's `TODO()`.
- Every public item documented in British spelling, with a sample that compiles and runs.
- Kotlin and Java stay compatible: a pull request that adds or changes a feature does so in both languages and both runners, and the two manifests differ only where section 15 allows.
- Annotations are the main way an application declares; the public builder is the core they are read into; whatever the types can refuse does not compile, and a compile-fail test shows it.

## Decisions

Each was put to the maintainer one at a time, with a recommendation, before any code.

1. **The language.** DECIDED (the maintainer, 2026-10-21, revised 2026-10-23): a core written in Kotlin, the primary implementation, a Kotlin layer, and a thin Java layer for synchronous workflows, with the five rules that keep the core reachable from Java; decision 14 makes Java's layer grow with Kotlin's. On 2026-10-21 Java was to be an equal of Kotlin in every part; on 2026-10-23 the maintainer first dropped Java ("if someone wants to keep up in java this is their subject"), then brought it back as synchronous only, on top of the Kotlin core, since Java still dominates enterprise backends ("Who it is for, and how the languages share it").

2. **Execution modes.** DECIDED (the maintainer, 2026-10-23): one mode per workflow, as in itinera-rs. A workflow is all synchronous or all `suspend`; `LocalExecutor` runs the first kind and `AsyncLocalExecutor` the second; `sync` and `async` are both claimed (section 11). Java writes synchronous workflows only. The options drafted before were two executors with the asynchronous one accepting both kinds and `CompletionStage` forms for Java beside the Kotlin ones, only `sync`, and only `async`. Revised on 2026-10-27: the ID generator and the reporter factories are synchronous in both modes, and `create()` is one ordinary function, as in itinera-rs, whose generator is a plain `Fn`, and itinera-ts, whose `@idGenerator` method returns a `string`; an asynchronous application awaits what it needs first and passes it in the initial data (section 10). A `suspend` `create()` awaiting a `suspend` generator was considered and dropped, so that the three languages share one pattern.

3. **How workflows are declared.** DECIDED (the maintainer, 2026-10-23): option 1.
   1. Annotations on plain classes implementing itinera's interfaces are the main API, read by reflection into descriptors that a public, typed builder makes; the builder is the core, used by the conformance runners and by applications that want no reflection. *(Recommended: it is Rust's shape, macros as syntax over a builder, so the book and the examples read alike across languages; Java developers know annotation-driven APIs from Spring and Jakarta EE, and both languages write them alike.)*
   2. A Kotlin DSL, type-safe builders such as `workflow<Orders>("orders") { step("charge") { ... } }`, as the main API, with a Java fluent builder. No reflection and more mistakes caught at compile time, but steps read as lambdas rather than classes, Java and Kotlin read differently, and it is further from Rust's macros.

4. **Checking annotations at compile time.** DECIDED (the maintainer, 2026-10-23): option 2, a KSP processor for Kotlin and a javac processor for Java sharing one set of rules. An application that leaves the processor out still compiles; its mistakes are refused, as `Violations` listing every one, when the workflow is first described, before any journey, so the one-line test that describes it fails the build's tests.
   1. No compile-time step in tier 1: what the annotations' types cannot catch is refused when the workflow is first described, and a test that describes it catches every mistake.
   2. As option 1, plus a KSP processor that reports the same mistakes as compile errors in Kotlin, in a stage of its own after the engine, as Rust's macros came in stage 8; a javac processor for Java would follow in the same stage. *(Recommended: it brings the annotations closest to Rust's macros and to "whatever we can stop from compiling", while the run-time checks, which the builder and hand-written descriptors need anyway, stay the source of truth.)*
   3. A KSP processor that generates the descriptors as code instead of reading annotations at run time, which also suits GraalVM native images and Android, and removes reflection from describing workflows; kotlin-reflect stays for the walk of data classes unless value walkers are generated too ("Android, later", point 1). The most work.

5. **What a value is.** DECIDED (the maintainer, 2026-10-21): values are the application's own objects, checked, copied and read by their runtime type, with nothing serialised and no Jackson (section 2), so `value-conversions` is not claimed, as proposal 0121 confirms (section 3). Proposal 0121 also made each receiver's copy its own, in place of the shared frozen copy first planned. The maintainer's words: "you shouldn't need to serialize and unserialize values... I think we can use RTTI." The options drafted before were Jackson 3 trees with the capability claimed, kotlinx.serialization, and JSON-shaped types only.

6. **The oldest JDK applications may use.** DECIDED (the maintainer, 2026-10-23): option 1, JDK 17.
   1. JDK 17. *(Recommended: Spring Boot 4 and most current libraries require 17, so it reaches the most applications; Kotlin's `@JvmRecord` and sealed classes work there; Java applications that want virtual threads or record patterns run on 21 or later, which needs nothing from the library.)*
   2. JDK 21, the LTS with virtual threads and record patterns.
   3. JDK 25, the newest LTS.

7. **The build tool.** DECIDED with decision 13 (the maintainer, 2026-10-23): Gradle with the Kotlin DSL, one build with a module per artifact; it is the Kotlin ecosystem's own, and what KSP, Dokka and ABI validation support first. Maven was the other option.

8. **Coordinates and packages.** DECIDED (the maintainer, 2026-10-23): option 1. The repository is decided (decision 13).
   1. Group `org.itinera-dev`, verified through the site's domain, packages under `org.itineradev.itinera`, such as `org.itineradev.itinera.journey.JourneyId`, since a package name cannot hold a hyphen. *(Recommended: the coordinates follow the domain the project owns.)*
   2. Group `io.github.itinera-dev`, verified through GitHub with no DNS change, packages under `io.github.itineradev`.

9. **Where the API reference lives.** DECIDED (the maintainer, 2026-10-23): javadoc.io, linked from the site, as itinera-rs's reference lives on docs.rs: it serves every release's javadoc jar with no hosting work. The other option was the site, at `/api/kotlin/` and `/api/java/` with `next/`, as TypeScript's, at the cost of a publishing step in every release.

10. **Where test support lives.** DECIDED with decision 13 (the maintainer, 2026-10-23): a separate artifact, `itinera-testing`, which an application adds to its test dependencies, the JVM's way of keeping test code out of production, as chapter 8, 8.1 point 2 asks. A `testing` package inside `itinera` was the other option.

11. **Rules refused by a signature check before any instance.** DECIDED (the maintainer, 2026-10-23): option 1. With the builder, the descriptor interfaces and the executors' types, `invalid-lifecycle`, `rescue-skip`, `journey-scope-request` and `mode-not-accepted` are impossible, so the runners cannot express their scenarios; annotated code can still write them, and they are refused when the workflow is described, before any instance exists. `no-instance` is not among them: a provider returns nothing as `noInstance()`, which both languages can write, so it runs ("Rules made impossible, and rules enforced at run time").
    1. Exclude all four, with proofs: a compile-fail test for the builder, the descriptor interfaces or the executor, and a test that the annotated form is refused when described, reading "through its types or signatures" in chapter 3, 3.8 point 1 as covering a signature checked before any instance. *(Recommended: none can ever reach a journey, which is what the exclusion promises; itinera-rs excludes these four too, with `no-instance`, which Rust's types rule out and the JVM's cannot.)*
    2. Give the builder a way to express them, untyped, so the runners run their scenarios, and make annotated code reach the journey too, aborting or refusing there. Every rule is then checked by conformance, at the cost of a part whose declared type is wrong reaching a journey.
    3. Exclude them only for applications that build with the processor of decision 4, and otherwise as option 2.

12. **Platforms.** DECIDED (the maintainer, 2026-10-23): JVM backends for tier 1, Kotlin in both modes and Java synchronous; Kotlin on Android, in both modes, one day, which the four points of "Android, later" keep open. iOS, which would mean Kotlin Multiplatform with no run-time reflection, is not planned.

13. **Repository and artifacts.** DECIDED (the maintainer, 2026-10-23): one repository, `itinera-dev/itinera-j`, one Gradle build with a module per artifact, every artifact at one version: `itinera`, the core, bringing only Kotlin's standard library; `itinera-kotlin`, with the asynchronous executor and everything Kotlin-specific, bringing kotlin-reflect and kotlinx.coroutines; `itinera-java`, from stage 3 (decision 14); `itinera-testing`; `itinera-checker`, the compile-time checks of decision 4; and `itinera-bom` (section 1).

14. **Java's conformance.** DECIDED (the maintainer, 2026-10-23, revised 2026-10-27): Java has its own conformance claim, with its own manifest, `conformance-java.json`, and report, since enterprise Java on backends matters most to the project, though Kotlin is the primary implementation. On 2026-10-23 one Kotlin runner was to prove both, with Java writing only the building, in a third column; on 2026-10-27 the maintainer chose a second runner written wholly in Java, step definitions, scenario model, building, reading and fixtures, so conformance proves the whole Java API, while the Kotlin runner keeps its two columns (section 15). On the same day the maintainer added four rules that keep the two languages compatible (section 15). The Java runner starts in stage 3 and grows with every stage, so the first release ships both languages. Android, when it comes, adds a run of the Kotlin runner on ART. The other option was Java's conformance starting only after the first Kotlin release.

15. **Java's nullability.** DECIDED (the maintainer, 2026-10-27): option 1. Proposal 0122 settled what a `null` result means; this decision is about `null` as a value read into a Java parameter.
    1. Honour JSpecify's `@NullMarked` and `@Nullable`: in marked Java code, a stored `null` read into a type not marked `@Nullable` is `wrong type`, as in Kotlin, and unmarked code admits `null` everywhere (section 2). *(Recommended: JSpecify 1.0 is the standard Spring Framework 7 and Kotlin both read, a small jar of annotations only, and it makes Java and Kotlin agree.)*
    2. Leave Java as it is: every Java reference parameter admits `null`, and the documentation says so.

16. **Annotation and interface names.** DECIDED (the maintainer, 2026-10-28): option 1. The annotations are the API applications write, so they take the names of Rust's macros, `@Workflow`, `@Step`, `@RescueStep`, `@StepPolicy`, `@WorkflowPolicy` and `@Role`, which the interfaces of the same names would block.
    1. Each interface whose name an annotation needs carries the `Itinera` prefix: `ItineraWorkflow`, `ItineraAsyncWorkflow`, `ItineraStep`, `ItineraRescueStep`, `ItineraStepPolicy` and `ItineraWorkflowPolicy`; every other interface keeps its plain name. A role interface is marked `@Role` instead of extending a marker. *(Recommended: the usual Java way of naming a library's base type, as `HttpServlet` is, keeping the specification's nouns.)*
    2. The `I` prefix on those interfaces, `IWorkflow` and `IStep`: short, but a .NET convention that Kotlin and Java rarely use.
    3. The `Definition` suffix, `WorkflowDefinition` and `StepDefinition`: close to the specification's "descriptor", which names another object.

17. **Reflection outside the readers.** DECIDED (the maintainer, 2026-10-28): option 1. Two checks of stage 4 keep a rule that types cannot hold by looking at a class: the builder takes and requests as a role only an interface marked `@Role`, and the asynchronous executor refuses an asynchronous part written in Java, which javac lets implement a `suspend` operation it cannot see, by looking for Kotlin's `@Metadata` or a lambda's hidden class.
    1. Allow the builders, `Requests.role` and the asynchronous executor, when it is made or admits an instance, to check what a class is marked or made as, with `isAnnotationPresent`, `isInterface` and `isHidden`, which read none of its members and need no keep rule on Android beyond the annotation itself. *(Recommended: both checks keep a rule of the specification or the plan, and cost nothing on Android once the annotations are kept.)*
    2. Keep reflection out of the builder and the engine and drop both checks: the builder would take any interface as a role, and an asynchronous part written in Java would fail only when called.

    Extended by the maintainer, 2026-10-28, in stage 5, by option 1 of a further question: the engine may read the class of an instance a service provider lends, its name and `isHidden`, to name the implementation that `service_provided` carries, giving the type the provider declares when the class is hidden. Reading a class's name reads none of its members either, and needs no keep rule, though R8 may shorten the name on Android.

Defaults taken without asking, which the maintainer may change: optional requests as `T?` in Kotlin and `Optional<T>` in Java, keys from parameter names when kept, interfaces rather than base classes, two workflow interfaces, one per mode, `ServiceLoader` for plugging in `itinera-kotlin`, events and results as `@JvmRecord` data classes under sealed interfaces, the tooling, Conventional Commits from the first commit, one long stack, and the stage order.

## Points to watch

- **A gap in the specification stops the work**, as in Rust and TypeScript: it goes to the maintainer and to `spec`, never decided in Kotlin or in Java.
- **`internal` leaks to Java.** Kotlin's `internal` is public in bytecode, and what the other artifacts call in the engine is public Kotlin; the module descriptor hides the engine on the module path, except from itinera's own modules, and the journey-abort exception is a private nested class, so no application can catch it by name.
- **A Kotlin application without `itinera-kotlin`.** Its annotated classes are refused when described, but a data class it captures as a value is only "not a value", which an abort reports with no error. The documentation's first page, the bill of materials and the getting-started example make the dependency hard to miss; stage 1's tech spec looks for a clearer signal.
- **Reflection and native images.** Reading annotations at run time needs reflection configuration under GraalVM native image; generating descriptors at compile time, which decision 4 left for later, would remove it. Out of scope for tier 1, said in the documentation.
- **Cancellation.** Telling the journey's own cancellation from a step's `withTimeout` is subtle (section 11), and stage 3 tests both.
- **`InterruptedException`** thrown by a blocking step is an abnormal termination. Whether the engine restores the thread's interrupt flag at once, which makes every later blocking call of the journey fail, or only when `run` returns, is for the tech spec of 0049.
- **Blocking inside `suspend` code.** A `suspend` step that calls a blocking library holds its dispatcher's thread, which no check can see. The documentation and the book show `withContext(Dispatchers.IO)`.
- **Copying calls application code, often.** A record or data class is rebuilt through its constructor, and a set's elements and a map's keys are hashed, once when a value is captured and again for every receiver (section 2). The documentation says a record's or data class's constructor and `init` blocks run whenever itinera copies it, so they must have no side effects, and that a constructor which copies a collection with `List.copyOf` hands receivers a list they cannot change. Stage 1 measures the cost of a copy per read.
- **Numbers do not widen.** An `Int` given where a `Long` is read is `wrong type`, as in Rust. Kotlin's literals are `Int` unless written `40L`, so this is the first mistake an application will make; the documentation and the book show it, and the abort names the key.
- **Unexpected results in Java** (proposal 0122). Kotlin does not check what a Java implementation of its interface returns, so the engine checks every result in both languages (section 11). One `@unexpected-result` scenario has a step hook return something that is not a lifecycle, which Java's types refuse, while every other scenario of the tag can be written in Java, and an exclusion covers a whole tag. [conformance#97](https://github.com/itinera-dev/conformance/issues/97), fixed in `v0.1.0-rc.18`, lets that sentence return a null-like value where the language allows nothing else, so the Java runner runs every scenario of the tag but the one tagged `@capability-async` too, an asynchronous step that resolves to no outcome, which no Java runner can write and which the Kotlin manifest excludes, and the Java runner's hook returns `null` there.
- **Running two columns in Cucumber-JVM.** cucumber-rs let the Rust runner copy each scenario per executor; Cucumber-JVM has no supported way to. Only the Kotlin runner has two columns. Stage 2 chose one run per mode merged into one report (section 15), over Cucumber's feature-parser extension point and over the features rewritten into a temporary directory with each scenario copied, since it needs neither an internal API nor a copy of the cases.
- **Two runners, written twice.** Every sentence of the cases is defined in Kotlin and again in Java, about 260 of them, so every stage that adds sentences writes them twice, and a change to the cases' sentences touches both runners. Each runner's test that no sentence is missing fails when it falls behind, and Cucumber fails a run that selects a scenario using an undefined sentence.
- **Roles through proxies.** A `Proxy` works only for interfaces, which roles are. Its handler unwraps the `InvocationTargetException` of the forwarded call and, as the one wrapper does, records `hook failed` with the operation's own error and message before the proxy could wrap a checked exception the interface does not declare, which Kotlin code may throw and Kotlin interfaces never declare, in an `UndeclaredThrowableException`. A role interface whose operations itinera may not call, in a package not open to it, is misdeclared when the workflow is described or built.
- **Implementation names** come from class names, which obfuscators change; the documentation says so.
- **Annotation names that Spring and Jakarta also use.** `@Service` and `@Provider` share their simple names with Spring's `@Service` and JAX-RS's `@Provider`, which the backends this plan serves import every day; Kotlin can alias an import, Java cannot. The tech specs of stages 4 and 8 settle the final names, considering names of itinera's own, such as `@UsesService` and `@ServiceProvider`.
- **Cucumber-JVM's JSON formatter** was in maintenance; stage 2 found Cucumber-JVM 8's `json` plugin built on the standalone formatter, writing the report `run-conformance` reads.
- **The cases move** to a newer candidate during this work; stage 11 adopts it.
