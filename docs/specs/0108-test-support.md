# 0108: Test support

Tech spec for [proposal 0108](https://github.com/itinera-dev/spec/blob/main/proposals/0108-test-support.md), implemented in [#36](https://github.com/itinera-dev/itinera-j/issues/36). Chapter 8 of the specification describes test support, and the [tier 1 plan](../tier-1-plan.md), section 14, holds what crosses proposals.

Status: done. Stage 2 added the recording reporters, which both conformance runners' dispatchers hold. Stage 3 added the step mock that both runners build their workflows from, stage 7 the policy mocks they build their policies from, stage 9 the rescue step mocks they build rescue steps from, and stage 10 adds fake providers, scripted runs, the recorders and the test's mistakes, and lists 108, with [0119](0119-attempt-mistakes.md), in both manifests, which claim `testing`.

## Where it lives

Test support is the artifact `itinera-testing`, which an application adds to its test dependencies only, as chapter 8, 8.1 point 2 asks (decision 10). It depends on `itinera`, and on `itinera-kotlin` and kotlinx.coroutines only at compile time (`compileOnly`, and `requires static` in its module descriptor), so a Java application's tests do not bring Kotlin's reflection or coroutines. The asynchronous reporter the recorders lend lets one call through at a time with a coroutine `Mutex`, as the reporter lent in a journey does. Its asynchronous parts can only be used with `itinera-kotlin` on the class path, which an asynchronous workflow has anyway.

Each part lives in a `testing` subpackage of the concept it belongs to, since a package cannot be split across two artifacts: the recording reporters and what a recorder keeps in `org.itineradev.itinera.report.testing`, the step mocks and the step event reporters in `org.itineradev.itinera.step.testing`, the policy mocks and the hook event reporters in `org.itineradev.itinera.policy.testing`, the contributions recorder and the test data bag in `org.itineradev.itinera.journey.testing`, the test instance builders and their fakes in `org.itineradev.itinera.instance.testing`, scripted runs in `org.itineradev.itinera.executor.testing`, and the test's mistakes, which belong to test support as a whole, in `org.itineradev.itinera.testing`.

Test support reaches the engine through three seams, public Kotlin in the engine's package, which the core's module descriptor exports only to the itinera modules, `itinera-testing` among them, as section 2 of the plan says:

1. **`Scripting`**, in `engine/Scripting.kt`. An instance implementing `ScriptedInstance` carries one, which the engine asks, for each attempt, what plays in place of the step's run, and tells each attempt handed to the construction of its step, with the values its requests found. The engine still resolves and builds every attempt; only the call to its run is replaced, by a `Play` that receives the attempt's contributor and the `Emits` its step reporter emits through. An instance that is not scripted plays nothing.
2. **`Lone`**, in `engine/Lone.kt`, a journey of the engine's own that no executor runs, whose contributor, step reporter and hook reporter behave as in a journey, so the recorders lend real handles: a reporter of a failing `Lone` interrupts every call, and setting `journey_id` interrupts that call and every later one.
3. **The descriptor interfaces.** Fake providers need no seam: the test instance builder wraps the workflow's descriptor, replacing only the call of each provider a fake replaces, so the engine resolves the provider's requests and calls the fake wherever it would call the provider.

## API

108 is listed in both manifests, so no public item below carries `@ExperimentalItineraApi`; each did until stage 10 listed it. The marker's own sample lives in the core's tests, since no listed API carries it.

- **`RecordingReporter`** is a `Reporter`, for synchronous workflows, made with its no-argument constructor. It keeps every event it receives, in order, and the latest value of each entry of global metadata, as chapter 8, 8.2 says, and it never fails. It offers `events`, a `List<Event>`; `globalMetadata`, a `Map<String, Any?>` keeping the order in which the keys were first set, so the journey ID comes first; and `path`, a `List<String>`. Each read is a new copy, so a test keeps what it read while the journey goes on. From Java, they read as `getEvents()`, `getGlobalMetadata()` and `getPath()`.
- **`AsyncRecordingReporter`** is its twin, an `AsyncReporter` for asynchronous workflows, with the same three properties. Its `report` and `setGlobalMetadata` are `suspend` functions marked `@JvmSynthetic`, as every asynchronous operation is.
- Both keep what they receive in one internal `Recording`, which locks on each read and write, since an asynchronous journey may report from more than one thread, one event after another.
- **`StepMock`**, in `org.itineradev.itinera.step.testing`, is a `SyncStepFactory` for tests, which the conformance runners build their workflows from. `StepMock.playing(first, vararg then)` makes one whose first attempt ends with `first`, each later one with the next of `then`, and every attempt after them with the last ending given; `StepMock.failingToBuild(errorMessage)` makes one whose build always throws an exception carrying the message, as a step whose constructor fails does. Each build makes a new step and counts as the next attempt of the script, across every journey that builds from the mock; `builds` tells how many builds succeeded. Both factories are static from Java, and Java reads `getBuilds()`.
- **`Ending`** says how an attempt of a step mock ends: `Ending.success()`; `Ending.failure(reason)`, or `Ending.failure(code)`; `Ending.skipped()`, `Ending.skipped(reason)` or `Ending.skipped(code)`; or `Ending.abnormalTermination(errorMessage)`, which throws an exception carrying the message from the step's run. It is a sealed interface, whose members are the data object `Success` and the records `Failure`, `Skipped` and `AbnormalTermination`. Its `outcome()` gives the outcome it stands for, or throws for an abnormal termination, so a test that writes real steps can end them the same way, as chapter 8, 8.5 point 10 asks.
- **`AsyncStepMock`** is the twin of `StepMock` for asynchronous workflows, an `AsyncStepFactory` with the same two factories and `builds`, which needs `itinera-kotlin`.
- **`RescueStepMock`** is the twin of `StepMock` for rescue steps, a `SyncRescueFactory` with `RescueStepMock.playing(first, vararg then)`, `RescueStepMock.failingToBuild(errorMessage)` and `builds`, played as a step mock is. **`RescueEnding`** says how its attempt ends: `RescueEnding.success()`, `RescueEnding.failure(reason)` or `failure(code)`, or `RescueEnding.abnormalTermination(errorMessage)`, a sealed interface of the data object `Success` and the records `Failure` and `AbnormalTermination`, with no skip, since a rescue step never skips; its `outcome()` gives the `RescueOutcome` it stands for, or throws for an abnormal termination. **`AsyncRescueStepMock`** is their asynchronous twin, an `AsyncRescueFactory`, which needs `itinera-kotlin`.
- **`StepPolicyScript`**, in `org.itineradev.itinera.policy.testing`, is a `PolicyFactory<StepPolicyMock>`, which says how each step hook of a policy ends. `StepPolicyScript.keepingDefault()` starts one whose four hooks keep the default; `onStepSuccess(ending)`, `onStepFailure(ending)`, `onStepRetry(ending)` and `onStepAbnormalTermination(ending)` give a hook its ending, and `failingToBuild(errorMessage)` makes every build throw an exception carrying the message, each returning a new script. Each build makes a new `StepPolicyMock`, whose four methods of the hooks' names give what each ending stands for, so a hook written as `{ policy, _ -> policy.onStepSuccess() }` plays its script.
- **`WorkflowPolicyScript`** is its twin for workflow policies, a `PolicyFactory<WorkflowPolicyMock>` started with `WorkflowPolicyScript.returning()`, with `onWorkflowSuccess(ending)`, `onWorkflowFailure(ending)` and `failingToBuild(errorMessage)`. A `WorkflowPolicyMock`'s two methods return, or throw.
- **`HookEnding`** says how a hook of a policy mock ends: `HookEnding.keepDefault()`, `HookEnding.finishWorkflow()`, `HookEnding.failWorkflow(reason)` or `HookEnding.failWorkflow(code)`, or `HookEnding.fails(errorMessage)`, which throws an exception carrying the message from the hook. Its types hold what each hook may return, as the hooks' own types do: `FailureHookEnding`, which the hooks other than `on step success` take, has no `FinishWorkflow`, and `WorkflowHookEnding`, which workflow hooks take, has only `KeepDefault` and `Fails`. `onSuccess()`, `onFailure()` and `played()` give what an ending stands for. Every factory is static from Java. A policy mock keeps nothing between calls; the runners count a policy's calls on their own wrapper around it.
- **`TestInstanceBuilder`**, in `org.itineradev.itinera.instance.testing`, creates a synchronous workflow's instance as `InstanceBuilder` does, from `TestInstanceBuilder.of(workflow)` for an annotated class or `of(descriptor, workflow)`, with the same `data`, `initialData`, `reporter`, `reporterFor`, `reportersGlobalMetadata` and synchronous `create()`, and adds `fakeProvider(name, service, fake)`: the provider named `name`, which must make `service`, is called through `fake`, a `Fake<T>` whose `provide()` returns a `Provided<T>`, as chapter 8, 8.4 says. A name the workflow does not have is the mistake `unknown provider`, and a provider making another service than `service` is `another service`, both thrown by `fakeProvider` itself, before the journey. **`AsyncTestInstanceBuilder`** is its twin for asynchronous workflows, taking an `AsyncFake<T>`, whose `provide()` is a `suspend` function. Taking the service's class is how the JVM checks the fake's service, since a lambda's type is erased.
- **`scripted(instance)`**, in `org.itineradev.itinera.executor.testing`, a function of the file `Scripted`, so Java calls `Scripted.scripted(instance)`, starts a `Script` for a synchronous instance, and, from Kotlin only, an `AsyncScript` for an asynchronous one. A script names a step with `step(name)`, and the next with `andStep(name)`, giving a `NamedStep`, whose attempts are chosen with `onAttempt(number)`, `onEveryAttempt()` or `onRemainingAttempts()`, attempt 1 when none is chosen. The attempts chosen then either `willRunForReal()`, or do, in this order, which the types hold: `willContribute(key, value)`, `willEmit(level, message)` or `willEmit(level, message, data)`, `willSetGlobalMetadata(key, value)`, and one ending, `willSucceed()`, `willFail(reason or code)`, `willSkip()`, `willSkipBecause(reason or code)` or `willTerminateAbnormally(errorMessage)`. Each ending gives a `StepScript`, which chooses further attempts of the step, names the next step, asks `ensureAllScripted()`, or runs: `run()` on a new `LocalExecutor`, or `run(executor)`; `AsyncScript.run` is a `suspend` function on an `AsyncLocalExecutor`. The interfaces are generic in what follows an ending, `NamedStep<StepScript>` or `NamedStep<AsyncStepScript>`, so one set of attempt interfaces serves both modes. Each mistake in writing is thrown by the call that makes it, and what the script leaves out by `run`, before the journey, as chapter 8, 8.5 points 7 and 8 say. A scripted ending is the step mock's `Ending`, converted to a `RescueEnding` for a rescue step, which turns a skip into the mistake `rescue step skips`.
- **`ScriptedRun`** holds the journey's `result`, and `step(name)` reads a step's or rescue step's **`StepRecord`**, throwing the mistake `unknown step` for a name the workflow does not have. A record's `attempts` are the **`AttemptRecord`**s of each attempt handed to its step's construction, and `attempt(number)` reads one, or `null`. An attempt record's `attempt` is its `Attempt`, and `input(key, type)` reads a value its step was built with as the data bag's `read` does.
- **The recorders.** **`Contributions`**, in `org.itineradev.itinera.journey.testing`, lends a `contributor` and reads what was contributed with `read(key, type)` and `keys`. **`TestDataBag`** is built with `with(key, value)`, each call giving a new bag, and lends `access`, a `DataBagAccess`; it is named apart from the journey's own `DataBag`, which only itinera makes, and refuses a value that is not one with `IllegalArgumentException`. **`StepEventReporter`**, in `org.itineradev.itinera.step.testing`, and **`HookEventReporter`**, in `org.itineradev.itinera.policy.testing`, lend a `reporter`, keep what is emitted as `emitted`, a list of **`Emitted`**, a record of its `Level`, message and data, and the `globalMetadata` set, and are made failing with `failing()`. **`AsyncStepEventReporter`** and **`AsyncHookEventReporter`** are their asynchronous twins.
- **`TestMistake`**, in `org.itineradev.itinera.testing`, is an unchecked exception whose message names each problem, and whose `problems` are the **`Mistake`**s found, a sealed interface of one record per kind, each with its `kind`, a **`MistakeKind`** whose `toString()` reads in words, such as `attempt left out`, and its `description`. A mistake names steps, attempts and providers as the test wrote them, a `String` and an `Int`, not as `StepName`, `Attempt` or `ProviderName`: a test can name a step or a provider the workflow does not have, or attempt 0, and every kind keeps the same shape, so a test compares problems with plain values.

## The path

`path` writes one line for each event of the journey's flow, exactly as chapter 8, 8.3 writes them, from an exhaustive `when` over every class of `Event`, so a new kind of event does not compile until it says whether it has a line. The flow is each attempt's outcome, each decision on a step and how the journey ended. Every other event has no line: the journey and attempts starting, hooks being called, inputs, services, contributions, emitted events and global metadata.

| Event | Line |
|---|---|
| `StepSucceeded` | `charge attempt 1 succeeded` |
| `StepFailed` | `charge attempt 1 failed: declined`, with the reason's code |
| `StepSkipped` | `charge attempt 1 skipped`, with `: ` and the reason's code when it has one |
| `StepAbnormalTermination` | `charge attempt 1 terminated abnormally: timeout`, with the error's message |
| `StepRetrying` | `charge retrying` |
| `StepGivenUp` | `charge given up: failure`, `abnormal termination` or `retries exhausted`, or `FailWorkflow from fraud_check`, naming the policy of the hook |
| `StepRescuing` | `charge rescuing with charge_rescue` |
| `StepRescued` | `charge rescued by charge_rescue` |
| `JourneySucceeded` | `journey succeeded`, or `journey succeeded, decided by early_exit` when a hook decided it |
| `JourneyFailed` | `journey failed at charge: declined`, with the reason's code, or the error's message when there is no reason |
| `JourneyAborted` | `journey aborted at charge: step could not be built`, or `journey aborted: reporter failed` when the abort concerns no step |

A refused journey emits no event, so its path is empty.

## Dependencies

None at run time beyond `itinera`. Test support adds no library. `itinera-kotlin` and kotlinx.coroutines, which `itinera-kotlin` brings at run time, are compile-only dependencies, and `itinera-kotlin` is a test dependency of the artifact's own tests.
