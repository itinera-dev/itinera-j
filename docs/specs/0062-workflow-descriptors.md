# 0062: Workflow descriptors, and executors independent of how workflows are written

Tech spec for [proposal 0062](https://github.com/itinera-dev/spec/blob/main/proposals/0062-workflow-descriptors.md), implemented in [#23](https://github.com/itinera-dev/itinera-j/issues/23). The [tier 1 plan](../tier-1-plan.md) holds what crosses proposals, sections 5 and 6 above all.

Status: started. Stage 3 added the descriptors, the builders of both modes and the annotation readers for a workflow of steps that take no requests. Stage 4 adds what steps request, then policies, input adapters, providers, rescue steps and the listing, and completes them. Until stage 5 resolves requests, a step's factory that reads one throws, saying this version does not resolve it yet.

## API

Until 62 is listed in both manifests, every public item below carries `@ExperimentalItineraApi`.

- **Modes.** `Mode` is sealed, with the data objects `Sync` and `Async`, in `org.itineradev.itinera.workflow`. Each is both the type a descriptor, a step, a reporter and an instance carry, such as `WorkflowInstance<Sync>`, and the value the executor compares with its own. A reporter is a `ReporterOf<M>`: `Reporter` is `ReporterOf<Sync>`, and `AsyncReporter` becomes `ReporterOf<Async>` with the asynchronous executor.
- **`WorkflowDescriptor<W, M>`** holds the name, the mode, the step descriptors and the ID generator. `WorkflowDescriptor.builder(type, name)` starts a synchronous one, and `build()` throws `Violations` with every violation it finds; stage 3 finds `duplicate step name`.
- **`StepDescriptor<M>`** holds the name, the factory, the retry budget and `retryOnAbnormalTermination`, named after the specification's `retry on abnormal termination`. A hand-written step whose retry budget is below 0, which the builder cannot make, is refused before the journey with `Violation.Misdeclared`. `StepDescriptor.builder(name, factory)` takes a `SyncStepFactory`, a `fun interface` whose `build(got)` returns a `SyncStepRun`, whose `run()` returns an `Outcome`. A Java lambda fits both: `got -> Outcome::success`. The step builder's `request(request)` declares each request the factory reads, in order, and the descriptor keeps them as `requests`.
- **The asynchronous builder**, in `org.itineradev.itinera.workflow.async` in `itinera-kotlin`: `asyncBuilder<W>(name)` starts an asynchronous workflow, and `asyncStep(name, factory)` an asynchronous step, whose `AsyncStepFactory`, in `org.itineradev.itinera.step.async`, builds an `AsyncStepRun` with a `suspend fun run()`. The factory itself is an ordinary function, as a constructor is, and the run alone awaits. The core's builders have internal constructors, so `itinera-kotlin` starts them through the engine's `Builders`. `asyncBuilder` is not reified: its type argument only fixes the builder's type. `builder<W>(name)`, in `org.itineradev.itinera.workflow.kotlin`, is the reified form of `WorkflowDescriptor.builder(W::class.java, name)`.
- **Requests.** `Request<K, T>`, in `org.itineradev.itinera.request`, is a typed token: what a part of kind `K` may request, read as `T` from the `Got<K>` its factory receives, as `got[AMOUNT]`. `Requests` makes them: `input(key, token)`, `optionalInput(key, token)`, whose answer is `null` when the data bag holds nothing under the key, `service(key, type)`, which makes a `ServiceRequest`, `contributor()` and `stepReporter()`. `itinera-kotlin` adds the reified `Requests.input<T>(key)`, `optionalInput<T>` and `service<T>`, in `request.kotlin`, and `Requests.asyncStepReporter()`, in `request.async`; `itinera-java` adds `JavaRequests.optionalInput(key, token)`, whose answer is an `Optional`, in `request.java`. Kinds are interfaces nothing implements, such as `StepKind<M>`, which extends `BuildKind`, `ContributorKind` and `StepReporterKind<M>`, so a synchronous step cannot declare the asynchronous reporter, and a part of another kind cannot declare what only a step may, at compile time. The factories are an object rather than static methods of `@Input`, because javac reads a static method of an annotation as an element of it, and then refuses every `@Input` that does not give it a value.
- **Handles.** `Contributor`, in `journey`, contributes a value under a key; `StepReporter`, in `step`, emits a step's own events and sets global metadata, and `AsyncStepReporter`, in `step.async` in `itinera-kotlin`, does so with `suspend` methods. A step declares the handles it reads, as it declares any other request.
- **Annotations.** A class implementing `ItineraWorkflow` is named by `@Workflow`, or after its simple name without it, and lists its steps with `@WithStep(step, name, retryBudget, noRetryOnAbnormalTermination)`, repeatable, in the order written. A step class is marked `@Step`, implements `ItineraStep`, has one constructor, whose parameters are its inputs, each marked `@Input(key, required)`, and one public method named `run` returning `Outcome`, whose parameters are its services, each marked `@Service(key)`, and its handles, recognised by their types: `Contributor`, and the step reporter of the workflow's mode. A key not written is the parameter's name. In Kotlin a nullable type makes an input optional, unless `required = true`; in Java an `Optional<T>` does, with `itinera-java`. A service is always required. The annotations keep Rust's names, `@Service` included, by the rule that the annotations applications write take the names of Rust's macros, though Spring has a `@Service` too: Kotlin can alias the import, and Java can write the full name. `@IdGenerator` marks the method producing the journey ID, which returns `String` and takes nothing or a `DataBag`.
- **`asyncDescriptorOf(type)`**, in `org.itineradev.itinera.workflow.async`, reads a class implementing `ItineraAsyncWorkflow` as `WorkflowDescriptor.of` reads an `ItineraWorkflow`, cached in a `ClassValue` of its own, through the engine's `Described.read`; `instance()` on `ItineraAsyncWorkflow` uses it. Its step factories call the `suspend` method `run` through Java reflection, handing it the caller's continuation with `suspendCoroutineUninterceptedOrReturn`, so a step that suspends resumes the caller, and what it throws, before or after it suspends, reaches the engine unwrapped.
- **`WorkflowDescriptor.of(type)`** reads the annotations once per class, cached in a `ClassValue`, and builds through the same checks as the builder. Every mistake is listed at once in `Violations`: a step class with no `run` or several, a `run` that returns what is not an outcome, a step class not marked `@Step`, several constructors, a constructor's parameter that is not an input, a `run`'s parameter that requests nothing, an input requested in `run`, the step reporter of the other mode, a key that is not written for a parameter whose name was not kept, an `Optional` without `itinera-java`, a request whose type no value can be, a service of a Kotlin type admitting `null`, a local or inner class that captures what its enclosing code holds, an abstract step class, an empty name, a retry budget below 0, several ID generators, an ID generator that returns what is not a `String`, takes what it cannot or is `suspend`, a return type admitting `null`, a step of the other mode, a member itinera cannot open, and a Kotlin class without `itinera-kotlin`. Those the specification does not name are `Violation.Misdeclared`, carrying the declaration and what is wrong with it. A service requested twice by one step is `service requested twice`, and a service that no provider gives is `service not provided`; until providers exist, every service is.

## How the classes are read

The core's reader uses Java reflection. For a Kotlin class, recognised by its `@Metadata`, it asks `KotlinClasses`, which `itinera-kotlin` provides through `ServiceLoader`, what each method declares that Java reflection cannot read: whether it is `suspend`, its return type as declared, and whether that admits `null`. For a constructor or a method, `KotlinClasses` also gives each parameter's Kotlin type and name, which Kotlin keeps in its `@Metadata`; for a Java class, the core reads the parameter's generic type and its JSpecify nullness, and its name only when the class was compiled with `-parameters`. Its nullness comes from the constructor's or method's own JSpecify mark first, then from its class's. An `Optional`'s value excludes `null`, so a `null` stored under its key is `wrong type`, whether the request was read from a parameter or made by `JavaRequests.optionalInput`. A parameter the compiler added, such as an inner class's outer instance or a local class's captured values, is dropped, and a class that has any is refused, since itinera cannot give what they hold. `StepRequests` turns each parameter into a request, and a `StepClass` keeps the constructor's and `run`'s, in order. Whether an `Optional` can be read is known through `JavaForms`, which `itinera-java` provides through `ServiceLoader`, so the core knows nothing of `Optional`'s answer. The factory of a step class builds the step with its constructor for every attempt, passing it what `got` answers for its inputs, and calls `run` by reflection with what `got` answers for its services and handles, unwrapping `InvocationTargetException` so the engine sees what the step itself threw. A `null` that a Java method returns reaches the engine as `null`, which it refuses as an unexpected result ([0122](0122-unexpected-results.md)).

The workflow name defaults to the class's simple name, as policies do in section 5 of the plan; obfuscators rename classes, so the documentation advises `@Workflow`.

## Dependencies

None of its own: kotlin-reflect, which reads Kotlin methods, belongs to [0056](0056-data-bag-values.md).
