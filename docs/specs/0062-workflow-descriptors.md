# 0062: Workflow descriptors, and executors independent of how workflows are written

Tech spec for [proposal 0062](https://github.com/itinera-dev/spec/blob/main/proposals/0062-workflow-descriptors.md), implemented in [#23](https://github.com/itinera-dev/itinera-j/issues/23). The [tier 1 plan](../tier-1-plan.md) holds what crosses proposals, sections 5 and 6 above all.

Status: done. Stage 3 added the descriptors, the builders of both modes and the annotation readers for a workflow of steps that take no requests. Stage 4 added what steps request, then policies and roles in the builders, then policies and roles in annotated classes, input adapters in the builders, then in annotated classes, providers, rescue steps, the listing and the reporters a workflow lists, and completed them; 62 is listed in both manifests at the end of stage 4. Until stage 7, nothing calls a hook. Until stage 5 resolves requests, a step's factory that reads one throws, saying this version does not resolve it yet.

## API

Every public item below carries `@ExperimentalItineraApi` though 62 is listed, as AGENTS.md allows: each is API of a proposal not listed yet, such as the modes of 0008 and 0012 and the listing of 0002, names such API, or holds a stand-in that a later stage replaces, such as the `Got` whose reads throw until stage 5 resolves requests.

- **Modes.** `Mode` is sealed, with the data objects `Sync` and `Async`, in `org.itineradev.itinera.workflow`. Each is both the type a descriptor, a step, a reporter and an instance carry, such as `WorkflowInstance<Sync>`, and the value the executor compares with its own. A reporter is a `ReporterOf<M>`: `Reporter` is `ReporterOf<Sync>`, and `AsyncReporter` becomes `ReporterOf<Async>` with the asynchronous executor.
- **`WorkflowDescriptor<W, M>`** holds the name, the mode, the step descriptors and the ID generator. `WorkflowDescriptor.builder(type, name)` starts a synchronous one, and `build()` throws `Violations` with every violation it finds; stage 3 finds `duplicate step name`.
- **`StepDescriptor<M>`** holds the name, the factory, the retry budget and `retryOnAbnormalTermination`, named after the specification's `retry on abnormal termination`. A hand-written step whose retry budget is below 0, which the builder cannot make, is refused before the journey with `Violation.Misdeclared`. `StepDescriptor.builder(name, factory)` takes a `SyncStepFactory`, a `fun interface` whose `build(got)` returns a `SyncStepRun`, whose `run()` returns an `Outcome`. A Java lambda fits both: `got -> Outcome::success`. The step builder's `request(request)` declares each request the factory reads, in order, and the descriptor keeps them as `requests`.
- **The asynchronous builder**, in `org.itineradev.itinera.workflow.async` in `itinera-kotlin`: `asyncBuilder<W>(name)` starts an asynchronous workflow, and `asyncStep(name, factory)` an asynchronous step, whose `AsyncStepFactory`, in `org.itineradev.itinera.step.async`, builds an `AsyncStepRun` with a `suspend fun run()`. The factory itself is an ordinary function, as a constructor is, and the run alone awaits. The core's builders have internal constructors, so `itinera-kotlin` starts them through the engine's `Builders`. `asyncBuilder` is not reified: its type argument only fixes the builder's type. `builder<W>(name)`, in `org.itineradev.itinera.workflow.kotlin`, is the reified form of `WorkflowDescriptor.builder(W::class.java, name)`.
- **Requests.** `Request<K, T>`, in `org.itineradev.itinera.request`, is a typed token: what a part of kind `K` may request, read as `T` from the `Got<K>` its factory receives, as `got[AMOUNT]`. `Requests` makes them: `input(key, token)`, `optionalInput(key, token)`, whose answer is `null` when the data bag holds nothing under the key, `service(key, type)`, which makes a `ServiceRequest`, `contributor()` and `stepReporter()`. `itinera-kotlin` adds the reified `Requests.input<T>(key)`, `optionalInput<T>` and `service<T>`, in `request.kotlin`, and `Requests.asyncStepReporter()`, in `request.async`; `itinera-java` adds `JavaRequests.optionalInput(key, token)`, whose answer is an `Optional`, in `request.java`. Kinds are interfaces nothing implements, such as `StepKind<M>`, which extends `BuildKind`, `ContributorKind` and `StepReporterKind<M>`, so a synchronous step cannot declare the asynchronous reporter, and a part of another kind cannot declare what only a step may, at compile time. The factories are an object rather than static methods of `@Input`, because javac reads a static method of an annotation as an element of it, and then refuses every `@Input` that does not give it a value.
- **Handles.** `Contributor`, in `journey`, contributes a value under a key; `StepReporter`, in `step`, emits a step's own events and sets global metadata, and `AsyncStepReporter`, in `step.async` in `itinera-kotlin`, does so with `suspend` methods. A step declares the handles it reads, as it declares any other request.
- **Policies.** `StepPolicyDescriptor<P, M>` and `WorkflowPolicyDescriptor<P, M>`, in `org.itineradev.itinera.policy`, hold a policy's name, the `PolicyFactory<P>` that builds it, a `fun interface` a Java constructor reference fits, and a `HookDefinition<M, P, K, R>` for each hook it defines, `null` for the others: the hook's requests in order and its call. A synchronous call is a `SyncHook<P, K, R>`, whose `call(policy, got)` returns the hook's own type, or a `SyncWorkflowHook<P, K>`, which returns nothing; `itinera-kotlin` adds `AsyncHook` and `AsyncWorkflowHook`, in `policy.async`, with `suspend` calls. `StepPolicyDescriptor.builder(name, factory)` and `WorkflowPolicyDescriptor.builder(name, factory)` start synchronous ones, and `asyncStepPolicy(name, factory)` and `asyncWorkflowPolicy(name, factory)`, in `policy.async`, asynchronous ones; each hook has its own builder method, with or without a list of requests. A builder throws `IllegalStateException` when a hook is defined twice or when `build()` finds no hook, since that misuse is the builder's own, not a violation of the workflow. The step builder's `policy(descriptor)` and the workflow builder's `policy(descriptor)` attach them, in the order their hooks are called; `StepDescriptor.policies` and `WorkflowDescriptor.policies` keep them.
- **What hooks return.** `OnSuccess` and `OnFailure` are sealed interfaces, which `KeepDefault`, a data object, both implement; `Lifecycle.FinishWorkflow` is an `OnSuccess` only, and `Lifecycle.FailWorkflow` both, so `FinishWorkflow` from a failure hook does not compile. Each also says what it decides through `keepsDefault`, `finishesWorkflow` (`OnSuccess` only) and `failsWorkflow`, for Java 17, which has no pattern matching over sealed types. Their companions make them: `keepDefault()`, `finishWorkflow()`, `failWorkflow(reason)` and `failWorkflow(code)`.
- **Hook requests.** `Requests` makes what hooks request, each with the kind that may make it: `fromStep`, `optionalFromStep`, `fromWorkflow`, `optionalFromWorkflow`, `journeyId`, `stepName`, `attempt`, `reason`, `optionalReason`, `error`, `optionalError`, `failureCause`, `retryCause`, `hookReporter`, `contributor` and `role(type)`. A hook's kind, `StepHookKind<M>`, `StepFailureKind<M>`, `StepRetryKind<M>` or `WorkflowHookKind<M>`, extends the kinds of what it may request, as chapter 6, 6.6 lists them, so `on step success` cannot request the failure's cause, nor a workflow hook the step's name, at compile time. `itinera-kotlin` adds reified `fromStep<T>`, `optionalFromStep<T>`, `fromWorkflow<T>`, `optionalFromWorkflow<T>` and `role<R>()`, in `request.kotlin`, and `asyncHookReporter()`, in `request.async`; `itinera-java` adds `optionalFromStep`, `optionalFromWorkflow`, `optionalReason` and `optionalError`, whose answers are `Optional`s. `HookReporter`, in `policy`, and `AsyncHookReporter`, in `policy.async`, are a hook's handles for its own events.
- **Roles.** A role is an interface marked `@Role`, in `policy`. The workflow builder's `role(type)` takes a `Class<in W>`, so a role the workflow object does not implement does not compile, and `WorkflowDescriptor.roles` keeps the roles provided. `Requests.role(type)` and `role(type)` throw `IllegalArgumentException` for a type that is not an interface marked `@Role`. A hook requesting a role that none of the workflow's roles is, or extends, is `role not provided`, `Violation.RoleNotProvided`, naming the policy and the role, found when the workflow is built, for a step policy as for a workflow policy, since chapter 6, 6.8 point 5 lets both request roles. A hand-written descriptor providing a role its workflow object does not implement is refused by `run`, `Violation.Misdeclared`.
- **Hooks defined twice.** Two policies attached to one step that define the same hook are `Violation.StepHookDefinedTwice`, naming the step, the hook and the policies in order, and two workflow policies that do are `Violation.WorkflowHookDefinedTwice`; both are `hook defined twice`. A hand-written policy descriptor that defines no hook is `Violation.Misdeclared`.
- **Mode.** `Parts.accepts(hook)` tells a hook of the executor's mode, as it tells steps and reporters, so `run` refuses a hook of the other mode, which only an unchecked cast hands over, with `mode not accepted`, naming it as `hook on step success of policy audit`.
- **Annotations.** A class implementing `ItineraWorkflow` is named by `@Workflow`, or after its simple name without it, and lists its steps with `@WithStep(step, name, retryBudget, noRetryOnAbnormalTermination, policies, rescue)`, repeatable, in the order written, its workflow policies with `@Workflow(name, policies)`, and its reporters with `@Workflow(reporters)`. A step class is marked `@Step`, implements `ItineraStep`, has one constructor, whose parameters are its inputs, each marked `@Input(key, required)`, and one public method named `run` returning `Outcome`, whose parameters are its services, each marked `@Service(key)`, and its handles, recognised by their types: `Contributor`, and the step reporter of the workflow's mode. A key not written is the parameter's name. In Kotlin a nullable type makes an input optional, unless `required = true`; in Java an `Optional<T>` does, with `itinera-java`. A service is always required. The annotations keep Rust's names, `@Service` included, by the rule that the annotations applications write take the names of Rust's macros, though Spring has a `@Service` too: Kotlin can alias the import, and Java can write the full name. `@IdGenerator` marks the method producing the journey ID, which returns `String` and takes nothing or a `DataBag`.
- **Policy classes.** A step policy class is marked `@StepPolicy(name)` and implements `ItineraStepPolicy`, whose methods `keepDefault()`, `finishWorkflow()` and `failWorkflow(reason)` or `failWorkflow(code)` make what its hooks return; a workflow policy class is marked `@WorkflowPolicy(name)` and implements `ItineraWorkflowPolicy`. A name not written is the class's simple name. Both are in `policy`, as are the hooks' annotations, `@OnStepSuccess`, `@OnStepFailure`, `@OnStepRetry`, `@OnStepAbnormalTermination`, `@OnWorkflowSuccess` and `@OnWorkflowFailure`, each marking one public method: an ordinary one in a synchronous workflow, a `suspend` one in an asynchronous workflow. A step hook returns `OnSuccess` from `on step success` and `OnFailure` from the others, and a workflow hook returns nothing. A hook method's parameters are its requests: data from the step or the workflow, marked `@FromStep(key, required)` or `@FromWorkflow(key, required)`, optional as an input is, a role, marked `@Role`, and the rest recognised by their types, `Contributor`, `JourneyId`, `StepName`, `Attempt`, `FailureCause`, `RetryCause`, `Reason`, `Throwable` and the hook reporter of the workflow's mode, each only where the hook's kind may request it. A `Reason` or `Throwable` admitting `null` in Kotlin, or an `Optional` of one in Java with `itinera-java`, is optional. The policy is built with its constructor that takes nothing. A workflow class provides every interface marked `@Role` that it, its superclasses or their interfaces implement. `@WithStep(policies = ...)` takes only classes implementing `ItineraStepPolicy`, and `@Workflow(policies = ...)` only those implementing `ItineraWorkflowPolicy`, so attaching one to the other does not compile. Every mistake in a policy class is listed in `Violations`, as `Violation.Misdeclared`: a class not marked as its kind of policy, a policy defining no hook, a hook that is not public, a method marked as several hooks, a hook defined in several methods, a hook of the other kind of policy, a hook returning what its kind does not or a type admitting `null`, a parameter that requests nothing, a parameter marked `@Input` or `@Service`, which a hook never requests, a request the hook's kind may not make, a role that is not an interface marked `@Role` or a Kotlin role admitting `null`, the hook reporter of the other mode, an `Optional` without `itinera-java`, an abstract class, a class without a constructor that takes nothing, and the mistakes a step's inputs can have: a key not written for a parameter whose name was not kept, a request whose type no value can be, a member itinera cannot open and a Kotlin class without `itinera-kotlin`. A hidden hook is found in the class and in its superclasses. A hook of the other mode is `mode not accepted`.
- **Input adapters.** `InputAdapterDescriptor<W, M>`, in `org.itineradev.itinera.workflow`, holds the adapter's name, an `AdapterName`, the names of the steps it is attached to, in order, its requests in order, and its call, an `InputAdapterCall<W, M>`: a `SyncInputAdapter<W>`, a `fun interface` whose `adapt(workflow, got)` returns `Supplied`, or an `AsyncInputAdapter<W>`, in `org.itineradev.itinera.workflow.async` in `itinera-kotlin`, whose `adapt` is `suspend`. `Supplied` is sealed: `Supplied.Value(value)`, whose `null` is the value null, and the data object `Supplied.FromDataBag`, the form of nothing of chapter 4, 4.2 point 3.1. `InputAdapterDescriptor.builder(name, step, adapter)` starts a synchronous one and `asyncInputAdapter(name, step, adapter)` an asynchronous one, each attached to its first step, since an adapter is attached to at least one; the builder's `step(name)` attaches it to another step, as often as it is called, so that one adapter naming a step twice can be written and refused, and `request(request)` declares what it requests. The workflow builder's `inputAdapter(adapter)` adds it, and `WorkflowDescriptor.inputAdapters` keeps them. Its kind, `InputAdapterKind`, in `request`, extends `StepNameKind`, `KeyKind`, `WorkflowDataKind`, `JourneyIdKind` and `DataBagAccessKind`, as chapter 3, 3.4 point 3 lists what it may request, so an adapter reading a contributor, a reporter or the attempt does not compile; `Requests.key()` and `Requests.dataBagAccess()` are the two requests only adapters make. `DataBagAccess`, in `journey`, reads the data bag as `DataBag.read` does, has no method that writes, and reads every key as absent once its call has returned; `itinera-kotlin` adds the reified `read<T>(key)`, in `journey.kotlin`. The engine's `DataBags.access(data)` makes one, for the engine and for test support. Two adapters with one name are `Violation.DuplicateAdapterName`, `duplicate adapter name`; two adapters attached to one step, or one attached to it twice, are `Violation.StepAdaptedTwice`, naming the step and the adapters once for each attachment, `step adapted twice`; an adapter attached to a step the workflow does not have is `Violation.InputAdapterForUnknownStep`, `input adapter for unknown step`, once for each adapter and step. `<step>_rescue` is a step the workflow has only while `<step>` has a rescue step. An adapter of a step that does not exist is not also `step adapted twice`. A hand-written adapter attached to no step is `Violation.Misdeclared`, `is attached to no step`. `Parts.accepts(adapter)` tells an adapter of the executor's mode, so `run` refuses one of the other mode, which an unchecked cast hands over, or an asynchronous adapter written in Java, with `mode not accepted`, naming it as `input adapter pricing`, since chapter 3, 3.6 counts input adapters among the parts the violation covers (spec#125, in the cases from `v0.1.0-rc.19`). A write through the access is impossible to express, in Kotlin and in Java, and both manifests list `bag-write` under `impossible`, each with its compile-fail test as proof: `bag-write` excludes "An adapter that writes through its access leaves the data bag unchanged", in `0060-input-adapters-attached-to-steps/data-bag-access.feature`, replaced in Kotlin by `an adapter's access to the data bag has no method that writes`, in `AdapterTypesTest.kt`, and in Java by `aJavaAdaptersAccessToTheDataBagHasNoMethodThatWrites`, in `JavaAdapterTypesTest.java`. An annotated workflow declares an adapter as a method of its class or a superclass marked `@InputAdapter(steps = [...], name = "")`, named after the method as Kotlin or Java writes it when `name` is empty, so an `internal` Kotlin method keeps its own name, returning `Supplied`, which `supply(value)` and `fromDataBag()` of `ItineraWorkflow` and `ItineraAsyncWorkflow` make; its parameters are its requests: the key, a `String` marked `@Key`, data marked `@FromWorkflow`, and the step's name, the journey ID and the data bag's access by their types. A method that is `suspend` in a synchronous workflow, or not in an asynchronous one, is `mode not accepted` when the workflow is described. One that names a step with an empty name, that returns what is not `Supplied` or admits `null`, a key that is not a `String`, or a Kotlin key admitting `null`, a parameter marked `@FromStep`, `@Role`, `@Input` or `@Service`, a contributor, and a parameter that requests nothing are each `Violation.Misdeclared` when the workflow is described, and so is `@InputAdapter(steps = [])`, as an adapter attached to no step. The adapters are read from the class before its superclass, each class's in the order of their methods' names, since Java reflection gives methods in no order, and a method overriding another replaces it, whether or not it is marked, even with narrower parameter types; a `private` or `static` method overrides nothing and is never replaced. Until stage 5, nothing calls an adapter.
- **Service providers.** `ProviderDescriptor<W, M>`, in `org.itineradev.itinera.service`, is sealed, and its scope is its type: a `JourneyProviderDescriptor` is called the first time a step it serves needs its service, and its instance is lent until the journey ends, and an `AttemptProviderDescriptor` is called for every attempt that needs it. Each holds the provider's name, a `ProviderName`, the key and the type of the service it supplies, the names of the steps it is attached to, in order, none when it serves every step, its requests in order, and its call, a `ProviderCall<M, W, K, T>`: a `SyncProvider`, a `fun interface` whose `provide(workflow, got)` returns `Provided<T>`, or an `AsyncProvider`, in `org.itineradev.itinera.service.async` in `itinera-kotlin`, whose `provide` is `suspend`. `Provided` is sealed: `Provided.Instance(instance, data)`, whose data the event saying it was provided will carry, and the data object `Provided.NoInstance`, the form of nothing of chapter 4, 4.9 point 6.2; Java sees `NoInstance` as a raw type, so `Provided.noInstance()` gives it typed for Java. `ProviderDescriptor.builder(name, key, type, provider)` starts a synchronous provider of journey scope and `ProviderDescriptor.perAttempt(name, key, type, provider)` one of attempt scope, and `asyncProvider` and `asyncPerAttemptProvider` the asynchronous ones; the builder's `step(name)` attaches it to a step, as often as it is called, so that one provider naming a step twice can be written and refused, and `request(request)` declares what it requests. The workflow builder's `provider(provider)` adds it, and `WorkflowDescriptor.providers` keeps them. Its kind says what it may request: `JourneyProviderKind<M>` the journey ID, data from the workflow and the provider reporter of its mode, `ProviderReporterKind<M>`, and `AttemptProviderKind<M>` also the step's name and the attempt, so a provider of journey scope reading either does not compile. `Requests.providerReporter()` gives a `ProviderReporter`, and `Requests.asyncProviderReporter()`, in `itinera-kotlin`, an `AsyncProviderReporter`, each emitting `journey_info`, `journey_warning` and `journey_error` and setting global metadata. A provider attached to a step serves that step for its key, in place of the provider of the key attached to no step, which serves every other step requesting it. A step whose service no provider serves is `service not provided`, and one whose provider supplies a type other than the one it requests is `wrong service type`, compared exactly, a primitive counting as its wrapper, naming the provider; two providers with one name are `duplicate provider name`; two attachments serving one step for one key, from two providers or one naming the step twice, or two providers of one key attached to no step, are `service provided twice`, naming the step, or none, and the provider of each attachment; a provider attached to a step the workflow does not have is `service provider for unknown step`, once for each provider and step, and is not also `service provided twice`; a hand-written provider of journey scope requesting the step's name or the attempt, which only an unchecked cast hands over, is `attempt request in journey scope`. `<step>_rescue` is a step the workflow has only while `<step>` has a rescue step. A provider of the other mode, which an unchecked cast hands over, or an asynchronous provider written in Java, is `mode not accepted`, naming it as `service provider gateway`, since chapter 3 gives providers a mode. A provider of journey scope requesting the attempt is impossible to express with the builders and the descriptor interfaces, in Kotlin and in Java, and both manifests list `journey-scope-request` under `impossible`, each with its compile-fail test as proof: `journey-scope-request` excludes "A provider of journey scope requesting the attempt number is refused", in `0095-services-provided-to-steps/admission.feature`, replaced in Kotlin by `a provider of journey scope cannot request the attempt`, in `ProviderTypesTest.kt`, and in Java by `aJavaProviderOfJourneyScopeCannotDeclareARequestOfTheAttempt`, in `JavaProviderTypesTest.java`. The annotations take the names of Rust's macros, as every annotation does: a step's service is marked `@Service`, and a provider method is marked `@Provider`, though Spring's `@Service` and JAX-RS's `@Provider` share those simple names; Kotlin can alias an import, and Java code naming both writes one in full. An annotated workflow declares a provider as a method of its class or a superclass marked `@Provider(perAttempt = false, steps = [], key = "", name = "")`, found and overridden as adapters are, of attempt scope when `perAttempt` is true, attached to the steps it names, and named and keyed after the method as Kotlin or Java writes it when `name` or `key` is empty. It returns `Provided` of the service's type, the type it is compared with, which `provide(instance)`, `provide(instance, data)` and `noInstance()` of `ItineraWorkflow` and `ItineraAsyncWorkflow` make; its parameters are its requests: data marked `@FromWorkflow`, and the journey ID, the step's name, the attempt and the provider reporter of its mode by their types. One of journey scope requesting the step's name or the attempt is `attempt request in journey scope`, which the reader alone can make, since its methods are not typed by kind. A method that is `suspend` in a synchronous workflow, or not in an asynchronous one, is `mode not accepted`, naming it as `service provider labels`; one that names a step with an empty name, that returns what is not `Provided`, admits `null` or names no class as its service, such as a raw `Provided` or one of a type variable, a parameter marked `@FromStep`, `@Role`, `@Input`, `@Service` or `@Key`, a contributor, the reporter of the other mode, an `Optional` without `itinera-java`, and a parameter that requests nothing are each `Violation.Misdeclared` when the workflow is described. Until stage 8, nothing calls a provider.
- **Rescue steps.** `RescueStepDescriptor<M>`, in `org.itineradev.itinera.workflow`, holds a rescue step's requests in order and its factory, a `RescueFactory<M>`: a `SyncRescueFactory`, a `fun interface` whose `build(got)` returns a `SyncRescueRun`, whose `run()` returns `RescueOutcome`, or an `AsyncRescueFactory`, in `org.itineradev.itinera.step.async` in `itinera-kotlin`, whose `AsyncRescueRun.run()` is `suspend`. It holds no name, no policies, no retry budget and no `retryOnAbnormalTermination`, since chapter 7, 7.1 point 1 gives a rescue step none. `RescueOutcome`, in `step`, is sealed and has no skip; until stage 5 adds failure, as it adds failure to `Outcome`, its one case is `RescueOutcome.Success`, which `RescueOutcome.success()` gives Java. `RescueStepDescriptor.builder(factory)` starts a synchronous rescue step and `asyncRescueStep(factory)`, in `org.itineradev.itinera.workflow.async`, an asynchronous one, and `request(request)` declares what it requests. The step builder's `rescue(rescue)` gives it to its step and throws `IllegalStateException` when called a second time, since a step has one at most, and `StepDescriptor.rescue` keeps it, `null` for a step without one. Its kind, `RescueKind<M>`, in `request`, extends `StepKind<M>`, `FromStepKind`, `ReasonKind` and `ErrorKind`, so a rescue step requests what a step may, and also the failed attempt's contributions, the failure's reason and the error with `fromStep`, `reason` and `error` and their optional forms, as chapter 7, 7.3 lists; a request of the attempt, the journey ID, the key or a hook's reporter does not compile. Its name is `<step>_rescue`, which the engine derives and counts among the workflow's steps: a declared step of that name is `duplicate step name`; an adapter or a provider may be attached to it, under the same violations as for a step, and a rescue step's services are served by the provider of the key attached to its name, or else by the one attached to no step, never by its step's, as chapter 3, 3.9 point 7 says; a step with both a rescue step and a retry budget above 0 is `Violation.RescuedStepRetried`, `rescued step retried`. A rescue step of the other mode, which an unchecked cast hands over, is `mode not accepted`, naming it as `rescue step pack_rescue`. A rescue step that skips is impossible to express with the builders and the descriptor interfaces, in Kotlin and in Java, and both manifests list `rescue-skip` under `impossible`, each with its compile-fail test as proof: `rescue-skip` excludes "A rescue step that skips aborts the journey", in `0003-rescue-steps/failing-rescue.feature`, replaced in Kotlin by `a rescue step never skips`, in `RescueTypesTest.kt`, and in Java by `aJavaRescueStepNeverSkips`, in `JavaRescueTypesTest.java`. An annotated workflow gives a step its rescue step with `@WithStep(rescue = ...)`, a `KClass<out ItineraRescueStep>`, so a class that is not a rescue step does not compile; its default, `ItineraRescueStep` itself, means none, since an annotation's member cannot be `null`. A rescue step class is marked `@RescueStep`, implements `ItineraRescueStep`, whose `succeed()` makes `RescueOutcome.Success`, has one constructor and one public method named `run` returning `RescueOutcome`, `suspend` exactly when the workflow is asynchronous. The constructor's parameters are what the rescue step requests while it is built, as chapter 7, 7.3 point 2 says: its inputs, each marked `@Input`, the data it requests from the step it rescues, each marked `@FromRescuedStep(key, required)`, in `step`, and the failure's `Reason` and its error, a `Throwable`, by their types; each is optional when its type admits `null` in Kotlin or, in Java with `itinera-java`, is an `Optional`, and `@Input` and `@FromRescuedStep` take `required = true` for a required request whose value may be `null`. The run's parameters are its services and handles, as a step's are. A run that is `suspend` in a synchronous workflow, or not in an asynchronous one, is `mode not accepted`, naming it as `rescue step charge_rescue`; a class not marked `@RescueStep`, a run returning `Outcome`, the one way annotated code can write a rescue step that skips, a constructor parameter that requests nothing, an `Optional` without `itinera-java`, and every mistake a step class can make are each `Violation.Misdeclared` when the workflow is described, and `@WithStep(retryBudget = 1, rescue = ...)` is `rescued step retried`. Until stage 9, nothing runs a rescue step.
- **Reporters the workflow lists.** Reporters belong to each instance, as chapter 3, 3.1 point 5 says, so the descriptor holds only how to make them: `WorkflowDescriptor.reporters` is a list of `ReporterFactoryOf<M>`, a `fun interface` in `org.itineradev.itinera.report` whose `create(journeyId)` returns a `ReporterOf<M>`, which `ReporterFactory` extends for a synchronous workflow and `AsyncReporterFactory`, in `itinera-kotlin`, for an asynchronous one, each narrowing its return type. The builder's `reporter(factory)` lists them, in order, and a Kotlin or Java lambda fits it, as in `builder.reporter { journeyId -> Printer(journeyId) }`, so no wrapper type stands between the application and its factory, as in itinera-rs and itinera-ts, whose builders take the reporter's type or class. `create()` makes each instance's own reporter of each, with its journey ID, before the reporters the instance builder is given, through the same checks: a factory that throws or returns `null` makes `create()` throw. An annotated class lists reporter classes with `@Workflow(reporters = [...])`, each built with its constructor that takes nothing, for every instance. The executor checks every reporter's mode before the journey, as it checks the instance's own, so a factory making a reporter that is only a `ReporterOf<M>`, neither `Reporter` nor `AsyncReporter`, is refused by `run` with `mode not accepted`. From Java, a factory whose reporter is itself a lambda is written as a `ReporterFactory`, such as `ReporterFactory printing = id -> event -> …`, since `ReporterOf` is no functional interface for the inner lambda to target.
- **The listing.** `WorkflowDescriptor.listing()`, a default method of the interface, so a hand-written descriptor has it too, reads the declaration alone, building and calling nothing, into a `ListedStep` for each step in order, as chapter 3, 3.1 point 2 says: its name, its `Position`, counted from 1, the names of its policies in order, the name of the input adapter attached to it, or `null`, the services it requests, each a `ListedService` of the key and the name of the provider that serves it, chosen as the executor chooses it, and, when it has a rescue step, its rescue section, a `ListedRescue` of the rescue step's name, its input adapter and its services, with no position and no policies, as chapter 7, 7.1 point 5 says. All four are in `workflow`; the three entries are `@JvmRecord` data classes, so Java reads them with accessors and tests compare them by value, and `Position.of(number)` refuses a number below 1, as `Attempt.of` does. A service no provider serves is left out, since such a workflow is refused before any journey. The listing is the same in both modes.
- **`asyncDescriptorOf(type)`**, in `org.itineradev.itinera.workflow.async`, reads a class implementing `ItineraAsyncWorkflow` as `WorkflowDescriptor.of` reads an `ItineraWorkflow`, cached in a `ClassValue` of its own, through the engine's `Described.read`; `instance()` on `ItineraAsyncWorkflow` uses it. Its step factories call the `suspend` method `run` through Java reflection, handing it the caller's continuation with `suspendCoroutineUninterceptedOrReturn`, so a step that suspends resumes the caller, and what it throws, before or after it suspends, reaches the engine unwrapped.

Every mistake is listed at once in `Violations`: a step class with no `run` or several, a `run` that returns what is not an outcome, a step class not marked `@Step`, several constructors, a constructor's parameter that is not an input, a `run`'s parameter that requests nothing, an input requested in `run`, the step reporter of the other mode, a key that is not written for a parameter whose name was not kept, an `Optional` without `itinera-java`, a request whose type no value can be, a service of a Kotlin type admitting `null`, a local or inner class that captures what its enclosing code holds, an abstract step class, an empty name, a retry budget below 0, several ID generators, an ID generator that returns what is not a `String`, takes what it cannot or is `suspend`, a return type admitting `null`, a step of the other mode, a reporter class of the other mode, which is `mode not accepted`, an abstract reporter class or one with no constructor that takes nothing, a member itinera cannot open, and a Kotlin class without `itinera-kotlin`. ## How the classes are read

The core's reader uses Java reflection. For a Kotlin class, recognised by its `@Metadata`, it asks `KotlinClasses`, which `itinera-kotlin` provides through `ServiceLoader`, what each method declares that Java reflection cannot read: whether it is `suspend`, its return type as declared, whether that admits `null`, and its name as Kotlin writes it, which Java reflection gives with a suffix for an `internal` method or one taking a value class. For a constructor or a method, `KotlinClasses` also gives each parameter's Kotlin type and name, which Kotlin keeps in its `@Metadata`; for a Java class, the core reads the parameter's generic type and its JSpecify nullness, and its name only when the class was compiled with `-parameters`. Its nullness comes from the constructor's or method's own JSpecify mark first, then from its class's. An `Optional`'s value excludes `null`, so a `null` stored under its key is `wrong type`, whether the request was read from a parameter or made by `JavaRequests.optionalInput`. A parameter the compiler added, such as an inner class's outer instance or a local class's captured values, is dropped, and a class that has any is refused, since itinera cannot give what they hold. `StepRequests` turns each parameter into a request, `HookRequests` each parameter of a hook method, and `AdapterRequests` each parameter of an input adapter's method, sharing `DataRequests` for inputs and data; a `StepClass` keeps the constructor's and `run`'s, in order. Whether an `Optional` can be read is known through `JavaForms`, which `itinera-java` provides through `ServiceLoader`, so the core knows nothing of `Optional`'s answer. The factory of a step class builds the step with its constructor for every attempt, passing it what `got` answers for its inputs, and calls `run` by reflection with what `got` answers for its services and handles, unwrapping `InvocationTargetException` so the engine sees what the step itself threw. A policy class's hooks are called the same way, through the `HookCalls` of the workflow's mode, on the policy its constructor built, and an input adapter's method through the `AdapterCalls` of the workflow's mode, on the workflow object. A `null` that a Java method returns reaches the engine as `null`, which it refuses as an unexpected result ([0122](0122-unexpected-results.md)).

The workflow name defaults to the class's simple name, as policies do in section 5 of the plan; obfuscators rename classes, so the documentation advises `@Workflow`.

## Dependencies

None of its own: kotlin-reflect, which reads Kotlin methods, belongs to [0056](0056-data-bag-values.md).
